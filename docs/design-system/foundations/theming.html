Foundation

Theming

Sweet Hand ships a light theme and a dark theme from one set of semantic tokens. A theme changes what the roles resolve to; components never know which theme they are in.

Overview

Light is a white canvas with near-black ink and one pepper red. Dark is a warm near-black canvas with light stone ink and a lighter pepper. Both are first-class: every contrast pair is checked in both, every component page shows both, and the mocks render in both.

  • One source. tokens/tokens.css holds light on :root and dark in two identical blocks. tokens/tokens.json is generated from it for other platforms.
  • Themes override semantic tokens only. Primitives (--palette-*) never change; components (--btn-*, --field-*, --alert-*) alias semantic tokens and follow automatically.
  • The OS decides by default. With no choice made, Sweet Hand follows prefers-color-scheme. A page or a subtree can force either theme with data-theme.

How themes apply

SituationResultMechanism
No attribute, OS in light modeLight:root values
No attribute, OS in dark modeDark@media (prefers-color-scheme: dark) { :root:not([data-theme="light"]) { … } }
<html data-theme="dark">Dark, whatever the OS[data-theme="dark"] { … }

data-theme="dark" on one elementThat subtree is darkThe dark block matches any element, so custom properties cascade from it (the side-by-side examples on these pages use this)

Each theme also sets color-scheme: light or color-scheme: dark, so native controls, date pickers, scrollbars and autofill follow without extra styles. Set the attribute before first paint to avoid a flash of the wrong theme:

<html lang="en-CA">
<script>
  // Before any stylesheet paints: apply a saved choice, else follow the OS.
  try { var t = localStorage.getItem('theme'); if (t === 'dark' || t === 'light') document.documentElement.dataset.theme = t; } catch (e) {}
</script>

Only store a choice when someone makes one; removing the attribute hands control back to the operating system. The mocks and these docs also accept ?theme=dark or ?theme=light and the t key; those are review conveniences, not product features.

Themes and breakpoints are independent. The responsive layout tokens (--layout-columns, --layout-gutter, --layout-margin, display sizes) change by viewport and are identical in both themes.

Token tiers

A value appears once as a primitive, gets meaning as a semantic token, and is scoped to one component as a component token. Each tier reads only from the tier above it.

TierPrefixSweet Hand exampleWho reads itThemes change it?
1 · Primitive--palette-*, --font-*, --line-height-*, --letter-spacing-*--palette-pepper-600, --palette-pepper-300, --palette-stone-950Semantic tokens onlyNever
2 · Semantic--color-*, --text-*, --space-*, --radius-*, --shadow-*, --duration-*, --ease-*, --z-*, --layout-*, --target-*, --control-height-*, --icon-*--color-accent: var(--palette-pepper-600) in light, var(--palette-pepper-300) in darkComponents and pagesYes: colours, shadows and color-scheme
3 · Component--btn-*, --field-*, --alert-*, --toast-tone.btn--primary { --btn-bg: var(--color-action); }One component in components.cssNo; follows its semantic alias

So the primary button's fill is --btn-bg → --color-action → --palette-stone-950 in light and --palette-stone-100 in dark. Changing the brand hue touches primitives; changing what "action" means touches the semantic tier; changing how buttons look touches the component tier.

Contrast and forced colours

Two more preferences adjust the active theme rather than replacing it.

Media queryWhat changes
prefers-contrast: moreDefault borders take --color-border-strong, so card and divider edges reach 3:1; muted text becomes default ink and subtle text becomes muted. Applies in both themes.
forced-colors: active (Windows High Contrast)The focus ring becomes Highlight and borders CanvasText. Buttons, fields, chips, tags, cards and filter triggers draw a system-colour border so their edges stay visible; the primary button uses Highlight/HighlightText; the selected filter and current tab are underlined because colour alone disappears.

Icons draw with currentColor and need nothing extra. Never use forced-color-adjust: none on content; it is reserved for the controls above, which then supply system colours themselves.

Adding a theme

A new theme, for example a high-contrast variant or a partner event microsite, is another [data-theme="<name>"] block that overrides semantic colour tokens and nothing else.

  1. Add any new raw colours as primitives in :root (--palette-*).
  2. Write [data-theme="<name>"] { … } overriding only --color-*, --shadow-* and color-scheme. Never override spacing, type, radius, motion or layout in a theme, and never component tokens.
  3. Override every role the light theme defines, not just the ones that look wrong: a missed role silently falls back to light.
  4. Run check_contrast.py (in .claude/skills/extracting-design-systems/scripts/); it picks up every [data-theme] block by itself. Make every pair in contrast-pairs.json pass with margin (aim for 4.8:1 on body text and 3.3:1 on edges).
  5. Keep pepper meaning "selected" and the ink button meaning "primary". A theme changes colours, not meanings.
  6. Regenerate tokens.json and check the mocks with ?theme=<name> where the mock script supports it.
[data-theme="high-contrast"] {
  --color-fg-muted: var(--palette-stone-950);
  --color-fg-subtle: var(--palette-stone-800);
  --color-border-default: var(--palette-stone-700);
  --color-border-strong: var(--palette-stone-950);
  --color-accent: var(--palette-pepper-700);
  --color-fg-accent: var(--palette-pepper-700);
  --color-focus-ring: var(--palette-pepper-800);
  /* …every other --color-* role… */
  color-scheme: light;
}

Consuming tokens.json

tokens/tokens.json follows the W3C Design Tokens Community Group (DTCG) format and is regenerated from tokens.css by tokens_to_json.py (in the same scripts folder); never edit it by hand.

  • Groups follow the names. --color-accent-subtle-hover lives at color.accent.subtle.hover; --duration-loop-fast at duration.loop.fast.
  • Each token has $type and $value: color, dimension, duration, cubicBezier, number, shadow, typography, fontFamily, fontWeight.
  • Aliases keep the tiers. A semantic token's $value is a reference such as {palette.pepper.600}, so tools can resolve or preserve the chain.
  • Sweet Hand metadata sits under $extensions["com.agent-toolkit"]: css (the custom property name), resolved (the final value in light) and themes, which holds each theme's override as themes.dark.$value plus its resolved value.
  • Light values are the defaults. Responsive overrides (columns, gutters, margins and display sizes at 48rem and 62rem) and the reduced-motion and contrast overrides are not in the JSON; platforms apply their own equivalents.
"accent": {
  "$type": "color",
  "$value": "{palette.pepper.600}",
  "$extensions": {
    "com.agent-toolkit": {
      "css": "--color-accent",
      "resolved": "#b5381f",
      "themes": { "dark": { "$value": "{palette.pepper.300}", "resolved": "#ff8f73" } }
    }
  }
}

To build platform constants, read $value for the light set and $extensions["com.agent-toolkit"].themes.dark.$value for the dark set, resolving {…} references through the same file. Web code should not consume the JSON at all: link tokens/tokens.css and read the custom properties.

Usage

  • Read colour by role (var(--color-fg-muted)), never by primitive (var(--palette-stone-700)) and never by hex (AGENTS.md).
  • Pick the role for what something is, not for how it looks in light: a selected chip is --color-accent-subtle, not "the pale pink".
  • Check every new screen in both themes before review; the mocks' t key and the docs toggle make that one keystroke.
  • Don't add @media (prefers-color-scheme) rules in components. If a component needs a different value in dark, it needs a semantic token.
  • Never dim, invert or filter food photos in dark. They are the content.

Accessibility

  • Both themes pass every pair in contrast-pairs.json; check_contrast.py must exit 0 for light and dark before any colour change merges.
  • Theme never carries meaning. Status, selection and errors read the same in both: words first, colour second.
  • Respect the person's choice: follow the OS unless they choose otherwise, and keep their choice across visits.
  • Forced colours and increased contrast are honoured in both themes (see above).

Tokens

Theming has no tokens of its own. The themed tokens are the semantic colours (--color-*), documented with light and dark values on Color, and the shadows (--shadow-color, --shadow-1 to --shadow-4), documented on Elevation. Everything else is identical in every theme.
