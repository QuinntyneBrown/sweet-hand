Layout

Mobile first, from 320px to 2560px. Five viewport classes from the L2 requirements, a 4, 8 and 12 column grid, and six page templates that every screen in the mocks is built from.

Overview

Most people will find a caterer on a phone, so every layout starts as a single column at 320px and adds columns, side panels and wider margins as space allows. The viewport classes come straight from the L2 requirements (XS, SM, MD, LG, XL), so a requirement such as "Given viewport LG, the listing shows 3 columns" maps to exactly one breakpoint in the CSS.

The layout tier (--layout-*) sits on top of the spacing scale. Columns, gutter, margin, top-bar height and section gap are redefined at each breakpoint in tokens.css; components read the tokens and never need their own media query for these values.

  • Phone (XS): one column, 16px margins, filters behind a button, sticky enquiry bar, dialogs as bottom sheets.
  • Tablet (SM–MD): two-up grids, 32px margins from MD, filters still behind a button, side sheets from MD.
  • Desktop (LG–XL): the filter column and side navigation appear, the caterer page gains its sticky enquiry panel, the inbox shows list and thread side by side, and the dashboard gains a preview pane at XL.

Viewport classes and breakpoints

L2 defines the classes by CSS pixel width: XS < 576px, SM ≥ 576px, MD ≥ 768px, LG ≥ 992px, XL ≥ 1200px. The system adds 2XL at 1440px, the point where the container stops growing. All queries are min-width (mobile first). Media queries cannot read custom properties, so components write these values literally, and only these values; "hide below" utilities use the breakpoint minus 0.01rem (for example max-width: 61.99rem).

Where these came from. The mocks' base kit mixed two breakpoint sets: the L2 set in the Sweet Hand components and a generic 40rem / 64rem pair in the inherited kit (dialog centring, toast position, sidebar layout, top-bar menu). Extraction normalised 40rem to 36rem (SM) and 64rem to 62rem (LG), so there are now exactly five breakpoints. 2XL (90rem) was added to name the container maximum the mocks already used.

Columns, gutters and margins

The column grid is a guide, not a cage. Most Sweet Hand screens are built from purpose-made layouts (the listing grid, the caterer layout, the work layout) whose tracks line up with the grid at each class; use .grid with .span-full for anything new, and .grid--auto (cards at least 18rem wide) for card collections.

Listing grid

Caterer cards go 1 / 2 / 2 / 3 / 3 across XS / SM / MD / LG / XL, with gaps growing from 24 × 48px to 40 × 64px. L2-005.4 asks for 4 columns at XL; the reference design shows 3 beside the filter column, so the mocks keep 3 and the conflict is open (mocks README, question 2).

Container and measure

.container centres content, caps it at --layout-container-max (1440px including margins, so 1280px of content at XL margins) and pads it with --layout-margin. Beyond 1440px the page simply gets wider margins: nothing stretches across a 2560px monitor.

--layout-measure (62ch) caps every paragraph, so text never runs wider than about 12 words even inside a wide container. Narrower containers exist for focused tasks:

Usage

  • Start from a template. A new screen is one of the six templates; if it is not, the structure belongs on the navigation and page structure pattern first.
  • Write mobile first. Base styles are XS; add @media (min-width: 36rem | 48rem | 62rem | 75rem) only. No other breakpoint values.
  • Read layout tokens, not numbers. Pad with --layout-margin, gap with --layout-gutter; they already change per class.
  • Let regions appear, not shrink. A sidebar or panel is either present at its full width (LG and up) or replaced by a button, sheet or sticky bar. Never squeeze a 15rem column into a phone.
  • Keep content in the container. Only banners, the site header background and full-bleed photo viewers run edge to edge.
  • Use min-width: 0 on grid children that hold long names or tables (.browse__results, .work-main already do) so they cannot force the page wider.
  • Use 100dvh for full-height layouts, sheets and the full-screen enquiry form so phone browser bars do not clip them.

Accessibility

  • Reflow (1.4.10, L2-064.2). No horizontal scrolling and nothing clipped at 320, 575, 576, 767, 768, 991, 992, 1199, 1200 and 2560px; wide tables scroll inside their own region.
  • Zoom (L2-069.3). At 200% in a 1280px window the page is 640 CSS px wide and gets the SM layout, with every function available.
  • Orientation (1.3.4). Layouts work in portrait and landscape; rotating keeps form input and scroll position (L2-064.3).
  • Focus not obscured (2.4.11). Sticky headers, the sticky enquiry bar and the reply box never cover the focused element: scroll-padding-top uses --layout-topbar-height, and pages with a sticky bar reserve bottom padding (.has-sticky-cta).
  • Safe areas. The header adds env(safe-area-inset-top); bottom bars add env(safe-area-inset-bottom); pages set viewport-fit=cover.
  • Source order matches visual order. Grid areas move the filter column beside the results at LG, but the DOM order (title, filters, results) is the same at every class, so keyboard and screen reader order never jump.
  • Landmarks. Every template has one <header>, one <main id="main"> reached by the skip link, side nav in <nav> with a label, and a <footer>.
