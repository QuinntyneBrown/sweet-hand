Color

A white canvas, near-black ink and one scotch-bonnet red that only ever means "selected / you are here". The food photos bring the colour; the interface stays out of their way.

Overview

Sweet Hand's palette is deliberately small. Almost every pixel is the white (or, in dark, stone-950) canvas and warm near-black ink, so the round food photos are the most colourful thing on any screen. One brand hue, pepper, marks where you are. Three quiet status hues carry success, warning and danger, and nothing else.

The hues are named after Caribbean kitchen staples, so a token name tells you its job before you look it up:

  • Stone: the warm greys of the reference's type, from the cast-iron pot to the flour on the board. Canvas, ink, text, borders and the "info" status.
  • Pepper: scotch bonnet red, the active "All" filter in the reference design. Selected and current state, focus, hovered links.
  • Callaloo: the leafy green. Success: "Published", "Replied", saved, completed checks.
  • Mango: ripe-mango amber. Warning: "Pending review", expiring certificates, and allergen tags.
  • Sorrel: the deep hibiscus red of the Christmas drink. Danger: errors, destructive buttons, "Declined", unread counts.

Colour comes in two tiers. Primitives (--palette-*) are raw values and are never read by a component. Semantic roles (--color-*) say what a colour is for, and are the only tier a theme overrides. Components alias semantic roles through their own tokens (--btn-bg, --alert-fg); see Theming.

Four rules carry the brand:

  1. Ink is action. The one primary button per screen is solid --color-action, like the wordmark.
  2. Pepper is "selected / you are here". The current filter, tab, chip, nav item and focus ring. Never a button fill, never decoration.
  3. Info is stone, not blue. The brand has one hue and it already means something, so neutral information stays grey.
  4. Sorrel is deeper and cooler than pepper, so an error can never be mistaken for a selection.

Primitive ramps

Each ramp runs lightest to darkest. Steps are only added where a semantic role needs them, so the ramps have gaps by design: stone has 15 steps because text, borders and dark surfaces all need fine control; the status hues have six to eight. Hover a ramp step to see its value.

Warm greys sampled from the reference's type, plus --palette-white and --palette-black. Light text sits at 950 (ink), 700 (muted) and 600 (subtle); dark text at 100, 350 and 400. Dark surfaces climb from 950 (canvas) through 900 (sunken) and 850 (raised) to 800 (subtle).

Where these came from. The mocks' draft (docs/mocks/assets/tokens.css) had a 13-step stone ramp and wrote five dark-theme values as raw hexes. The draft's stone-400 and stone-500 moved up one step to make room: control edges are now stone-500 and the old 500 step is gone (see Accessibility for why light subtle text moved to stone-600).

Status colours

Why info is stone

Most systems make "info" blue. Sweet Hand has exactly one hue with a meaning, so a blue would be a second brand colour competing with the photos, and a pepper info banner would look like a selection. Neutral announcements ("Scheduled maintenance", "Export requested") are stone-50 with stone-800 text: calm, legible and clearly not an error.

Pepper and sorrel side by side

Both are reds, so they are kept apart on two axes. Sorrel is darker (sorrel-600 is 7.4:1 on white against pepper-600's 5.9:1) and cooler (it leans toward hibiscus magenta, pepper toward orange). Errors also always arrive with the danger icon and words, while selection arrives with bold text or a filled chip.

Stars, photos and scrims

A filled star is ink and an empty star is stone-500 (stone-600 in dark), so the empty outline still reads as part of a control at 3:1. The mocks' draft used stone-300 (light) and stone-700 (dark), 1.7:1 and 2.1:1, which failed 1.4.11 on the star input in dialogs/review. Photos sit on --color-bg-photo until they load; any text over a photo sits on --color-bg-scrim in --color-fg-on-scrim. That role is new: components used to read --palette-white directly, which broke the "components never read primitives" rule.

Light and dark

Dark theme is not an inversion. It keeps the same hierarchy with different steps: the canvas becomes stone-950, text becomes stone-100, raised surfaces lift to stone-850 (shadows hardly read on near-black), pepper and the status hues jump to their light 300 steps, and every solid fill takes dark text. Both themes use the same component CSS; only the --color-* tier changes.

Usage

  • Read roles, never primitives or hex. Write color: var(--color-fg-muted), never var(--palette-stone-700) and never a hex. The design-system checker fails any raw colour in component CSS.
  • One ink fill per screen. The primary button is the only solid ink surface besides small ink marks (count bubbles, "Cover" tags, your own message bubble).
  • Pepper only for state. Selected, current, focused, hovered link. If removing the pepper would not change what the person thinks is selected, it should not be pepper.
  • Tint before solid. Status meaning uses the tinted -bg with -fg text. Solids are for small marks (badges, checks) and the destructive button inside a confirmation dialog.
  • Muted for the supporting line. Every caterer card is name in default ink, "cuisine · area" in muted. Do not add a third colour.
  • Subtle is the floor for text. Never place subtle text on a tint other than sunken or subtle; those are the only checked backgrounds.
  • Mango for allergens. Allergen tags use the warning tint with text and an icon; dietary tags ("Vegan", "Halal") stay neutral.
  • Photos own the colour. Do not tint photo frames, overlay brand colour on food, or add coloured section backgrounds behind photo grids.

Adding a brand theme

A theme overrides the semantic tier only. To make, for example, a high-contrast or partner theme:

  1. Add any new primitives your theme needs to tokens/tokens.css as --palette-* steps (never inline hexes in the theme block).
  2. Add a block [data-theme="partner"] { … } that reassigns every --color-* role in the dark block's list, plus color-scheme.
  3. Keep the meanings: one action colour, one "selected" colour that is never a button, info neutral, danger distinct from the selected hue.
  4. Run scripts/check_contrast.py for the new theme; every pair in contrast-pairs.json must pass. Add a pair whenever you introduce a new foreground/background combination.
  5. Regenerate tokens.json with scripts/tokens_to_json.py and check the theme toggle on this page.
[data-theme="partner"] {
  --color-accent: var(--palette-partner-600);
  --color-fg-accent: var(--palette-partner-600);
  --color-accent-subtle: var(--palette-partner-50);
  --color-focus-ring: var(--palette-partner-600);
  /* …every other --color-* role… */
  color-scheme: light;
}

Accessibility

Sweet Hand meets WCAG 2.2 AA in both themes: 4.5:1 for text (1.4.3), 3:1 for large text, control edges, focus indicators, meaningful icons and state marks (1.4.11, 2.4.11), and never colour alone (1.4.1, L2-069.5). Every foreground/background combination a component uses is listed in tokens/contrast-pairs.json and checked in both themes by scripts/check_contrast.py. The table below recomputes each ratio live in your browser.

Corrections made during extraction

  • Light subtle text was stone-500 #76726c: 4.8:1 on white, but 4.39:1 on the sunken enquiry summary (pages/thread/default) and 4.06:1 on hovered filter rows (pages/caterers/default). It is now stone-600 #6b6863, which passes on every checked background (pairs 64 and 65).
  • Empty stars were raised to 3:1: stone-500 light, stone-600 dark (pair 70).
  • Text on photos now reads --color-fg-on-scrim on --color-bg-scrim; the ratio is computed with the scrim composited on white, the worst case for any photo (pair 66).
