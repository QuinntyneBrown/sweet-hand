Accessibility

Sweet Hand meets WCAG 2.2 AA by construction: the tokens, components and checks below make the accessible choice the default one, so a page built from the system starts compliant.

Overview

People find caterers for weddings, funerals and family Sundays on whatever device is in their hand, often a phone, sometimes with a screen reader, magnification, a switch or a keyboard. The target is WCAG 2.2 AA (AGENTS.md). L1-019 and L2-066 to L2-069 name WCAG 2.1 AA; 2.2 adds focus not obscured, target size, dragging alternatives, redundant entry and accessible authentication, and the mocks already meet them, so the system commits to 2.2.

  • Built in, not bolted on. Contrast is solved in the tokens (every pair is checked in both themes), focus is one shared ring, the default control is 44px tall, and reduced motion is a token change.
  • Native first. Real <button>, <a>, <label>, <input>, <details>; ARIA only fills gaps, following the WAI-ARIA Authoring Practices pattern named on each component page.
  • Every component page answers the same seven questions (see the contract), so nothing is left to the implementer's memory.

Perceivable

RequirementSCSweet Hand commitment
Text contrast1.4.3Body, label, metadata and placeholder text are at least 4.5:1 on every surface they sit on, in both themes; large text (24px, or 18.66px bold) at least 3:1. Every pair is declared in tokens/contrast-pairs.json and checked. Text on food photos sits on --color-bg-scrim so it stays at 4.5:1 whatever the photo (L2-069.2).
Non-text contrast1.4.11Input and secondary button edges (--color-border-strong), the focus ring, the switch track, meaningful icons, empty rating stars and chart bars are at least 3:1. Hairline dividers and card edges are decorative and documented as exempt.
Use of colour1.4.1Pepper red marks "selected", and selection is also shown by weight, a check or aria-pressed/aria-current. Statuses (Open, Replied, Declined, Published) are words in a label, not dots. Links in text are underlined. Optional fields say "(optional)" after the label.
Resize and reflow1.4.4, 1.4.10All sizes in rem. Every page reflows to 320px CSS width with no horizontal scrolling, and works at 200% zoom in a 1280px window (L2-064.2, L2-069.3). Only data tables scroll sideways, inside their own wrapper.
Text spacing1.4.12Nothing clips at 1.5 line height, 2× paragraph spacing, 0.12em letter and 0.16em word spacing: no fixed heights on text containers, long caterer names wrap and clamp to two lines with the full name available.
Images1.1.1Food photos use the caterer's own caption as alt (L2-068.1), e.g. "Chicken pelau in a steel pot with lime and cucumber chutney". Thumbnails that repeat a nearby caption get alt="". Icons are aria-hidden="true"; icon-only controls carry aria-label.
Orientation; animation1.3.4, 2.3.3No orientation lock; rotating keeps form input and scroll position (L2-064.3). Motion follows reduced motion.
Input purpose1.3.5autocomplete on name, email, phone, postal code and new and current passwords. Postal codes use autocapitalize="characters", guest counts inputmode="numeric", dates type="date" (L2-065.2).
Info and relationships1.3.1Headings in order, lists as lists, facts as <dl>, tables with <th scope>, groups of choices in <fieldset> with a <legend>.

Operable

RequirementSCSweet Hand commitment
Keyboard2.1.1, 2.1.2Everything works with Tab, Shift+Tab, Enter, Space, Escape and arrows where a pattern calls for them. Only open dialogs and sheets trap focus, and Escape releases them (L2-067.1).
Skip link and landmarks2.4.1"Skip to main content" is the first focusable element on every page (L2-067.3). Pages use header, nav (named when there are several), main and footer.
Focus visible2.4.7One ring for everything: a 2px --color-focus-ring outline, offset 3px, on :focus-visible. At least 3:1 against what surrounds it, in both themes (L2-067.2). See Focus.
Focus not obscured2.4.11scroll-padding-top matches the header height; the sticky enquiry bar and phone reply box reserve space at the bottom; toasts sit in a corner and never cover the focused field.
Focus order2.4.3DOM order is visual order at every breakpoint; no positive tabindex. Dialogs, sheets and the photo viewer move focus in when they open and back to their trigger when they close (L2-067.4).
Target size2.5.8Every target is at least 24 × 24px. On phones and small tablets (below 48rem) every target is at least 44 × 44px with 8px between neighbours (L2-065.1). See Target sizes.
Dragging2.5.7Photo and dish order can be changed with "Move up" and "Move down" buttons; nothing requires a drag. The gallery carousel can be swiped or stepped with Previous and Next.
Timing2.2.1, 2.2.2Success toasts stay at least 8 seconds and pause on hover and focus; error toasts never auto-dismiss. Operator sessions warn 5 minutes before they end and keep unsaved reasons. Nothing auto-advances.
Titles and headings2.4.2, 2.4.6A unique <title> per page that names the caterer, thread or screen, one <h1>, headings in order.
Link purpose2.4.4Link text makes sense alone: "View Pelau House", not "click here". Repeated "Edit" actions add the object in aria-label or a visually hidden span.
Pointer cancellation2.5.2Actions fire on click, never on pointer down.
Hover and focus content1.4.13Tooltips appear on hover and focus, stay while hovered, and close with Escape; on touch the same information is available by tap (L2-065.3).

Understandable

RequirementSCSweet Hand commitment
Labels3.3.2A visible <label> for every field, programmatically linked; placeholders are examples, never labels (L2-068.2).
Error identification and suggestion3.3.1, 3.3.3Error text names the problem and the fix ("Enter a whole number of guests from 1 to 5,000"). Fields get aria-invalid="true" and aria-describedby pointing at the error; a summary at the top links each error to its field and receives focus on submit (L2-068.3). See error messages.
Error prevention3.3.4Removing a dish or photo, declining an enquiry, deleting an account, and suspending or removing a caterer are confirmed in a dialog; removals offer Undo where possible; removing a caterer asks for the business name to be typed.
Redundant entry3.3.7A restored enquiry draft keeps everything that was typed ("Welcome back, Marcia"); details already on the account are never asked for again in the same flow.
Accessible authentication3.3.8No puzzles or cognitive tests. Paste and password managers work; two-step verification accepts an authenticator code or a security key.
Consistent navigation and help3.2.3, 3.2.4, 3.2.6The same header, side navigation and footer, in the same order, with the same names on every page of an area. Help and privacy links sit in the footer everywhere.
On input3.2.2Choosing a filter updates results in place and announces the count; nothing navigates or submits on change alone. Phone filters apply only when "Show 60 caterers" is pressed.
Language3.1.1, 3.1.2<html lang="en-CA">. Phrases in another language carry their own lang, for example Haitian Creole lang="ht" in a Ti Kay dish description.

Robust

RequirementSCSweet Hand commitment
Name, role, value4.1.2Filter list items are buttons with aria-pressed; the current page and section use aria-current; disclosure triggers use aria-expanded; busy buttons use aria-busy="true" and keep their label; dialogs use role="dialog", aria-modal="true" and aria-labelledby.

Checklist for every screen

  • One <h1>, a unique title and a working skip link.
  • Every photo has the caterer's caption as alt, or alt="" if it repeats nearby text.
  • Every control has a visible label or an aria-label naming its object.
  • Tab order follows reading order at 360px and at 1280px.
  • Every status is in words, not only colour.
  • No horizontal scroll at 320px; nothing lost at 200% zoom.
  • Dialogs move focus in, trap it, close on Escape and return focus.
  • Errors are summarised, linked and announced.

Focus

One focus ring serves every interactive element: a 2px outline in --color-focus-ring (pepper red, the "you are here" colour), drawn 3px outside the element so it never touches the fill. Inputs draw it at 0 offset and colour their border to match; menu items draw it inset; on the inverse toast it switches to the toast's text colour. It appears only for keyboard focus (:focus-visible), never on mouse click.

Target sizes

The default control is 44px tall (--control-height-md), so every button, field, filter item and icon button already meets the phone target. Two tokens set the floor and the comfortable size.

24px floor (--target-min) · 44px comfortable (--target-comfortable) · a 44px icon button · a 44px button
WhereMinimum targetSpacing
Below 48rem (XS, SM: phones and small tablets)44 × 44px for every control, including toast and banner close buttons, chip remove buttons, small buttons and menu items (L2-065.1)8px between neighbouring targets
48rem and up44px by default; 36px (--control-height-sm) allowed for row actions, chips and menu items; 24px for inline close and dismiss buttonsSmall targets keep 8px between them; a 24px target has no other target within its 24px circle (WCAG 2.5.8)
Text links in a paragraphExempt (inline, WCAG 2.5.8)–

The visible glyph can be smaller than the target: a 20px icon sits centred in a 44px .icon-btn, and a checkbox's whole label row is its target. Never shrink padding to fit more controls in a row on a phone; wrap or move secondary actions into a menu instead.

Testing procedure

Automated

  1. Contrast. check_contrast.py checks every pair in tokens/contrast-pairs.json against tokens.css in light and dark. Both must exit 0. Add a pair whenever a component puts a new foreground on a new background.
  2. Structure. check_design_system.py checks every page for lang, one <h1>, a main landmark, labels on every field, names on every button and link, alt on every image, resolving links and no raw colours.
  3. Product pages. axe-core with WCAG A and AA rules on every page template at XS and XL, in every state the acceptance tests cover, including open dialogs, errors and empty states; any violation fails CI (L2-066). Playwright runs in Chromium only.

Manual, for every new component or screen

  1. Keyboard. Unplug the mouse. Tab through every example: is the ring always visible and the order sensible? Open and close each dialog with Enter and Escape; does focus come back?
  2. Screen reader. NVDA with Firefox or Chrome on Windows and VoiceOver on iOS Safari (L2-066.3). Check one dialog, one form with errors, the filter list and one table: names, roles, states and announcements.
  3. Zoom. 200% in a 1280px window (nothing lost, L2-069.3) and 400% (equivalent to 320px: reflow, no sideways scroll except tables).
  4. Reduced motion. Emulate prefers-reduced-motion: reduce; nothing slides, scales or shimmers, and the busy spinner still turns.
  5. Forced colours. Emulate forced-colors: active; controls keep visible edges, the focus ring uses Highlight, and the selected filter is underlined.
  6. Touch. On a real phone at 360px, check every target is 44px and nothing depends on hover.
  7. Text spacing. Apply the 1.4.12 bookmarklet; nothing clips or overlaps.

The component contract

Every component page has an #accessibility section with the same seven parts, in this order. A component is not "stable" until all seven are written and true.

PartWhat it answers
1. Role and patternThe native element or ARIA pattern used, linked to the WAI-ARIA Authoring Practices pattern.
2. KeyboardA key map: Tab, Shift+Tab, Enter, Space, Escape, arrows, Home and End, type-ahead, with the effect of each.
3. FocusWhere focus starts, where it goes on close or removal, and how the ring is drawn.
4. LabellingWhat must be labelled, how, and what a screen reader announces.
5. ContrastThe token pairs involved with live ratios in both themes; every pair exists in contrast-pairs.json.
6. MotionWhat animates, with which tokens, and what happens with reduced motion.
7. TouchTarget sizes at each breakpoint, spacing, and the alternative to any hover-only behaviour.

Usage

  • Never remove the focus outline, and never replace it with a colour change alone.
  • Never use tabindex above 0; use tabindex="-1" only on things that receive focus by script (error summary, dialog heading, thread heading).
  • Never put information only in a tooltip, a placeholder or a colour.
  • Never auto-dismiss an error, and never move focus without a reason the person caused.
  • When in doubt, use the native element and the component's existing markup; it already passes.
