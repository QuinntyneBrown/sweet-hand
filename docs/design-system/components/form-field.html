Form field

The wrapper around every control: a visible label, the control, one message slot for an error or warning, and help with an optional character counter, in that order with 4px between parts.

Overview

Every text field, textarea, select and file upload sits in a .field. The field gives the control its label and its descriptions, and keeps them in the same order on every form: the enquiry dialog, business details, the food handler certificate, the operator's reason boxes.

  • Label is always visible, above the control. Placeholders are hints, never labels.
  • Optional is the marked case. Most Sweet Hand fields are required, so "(optional)" goes on the few that aren't, such as "Postal code (optional)" in the enquiry or "Copy of certificate (optional)".
  • Message slot holds at most one message, directly under the control: an error (.field__error, sorrel, blocks submission) or a warning (.field__warning, mango, lets it through: "This caterer usually serves 20–300 guests").
  • Help (.field__help) says what a good answer looks like: "At least 2 days from today", "Pelau House serves 20–300".
  • Counter (.field__counter) shows "35 / 2,000" on long text and turns sorrel past the limit (data-over).

Groups of checkboxes or radios use a <fieldset> and <legend> instead (see checkbox and radio group); a single consent checkbox sits in a .field without a separate label. Layout across fields (rows, sections, actions) is form layout; validation timing and the error summary are the forms pattern.

Anatomy

  1. Label<label class="field__label" for>; --text-label, --color-fg-default. Wraps, never truncates.
  2. Optional marker.optional inside the label: "(optional)", regular weight, --color-fg-subtle. Part of the accessible name.
  3. ControlInput, textarea or select, full width, 4px below the label.
  4. Message slotOne .field__error or .field__warning, 4px below the control, before the help. Icon and words; never colour alone.
  5. Help.field__help, --text-body-sm, --color-fg-muted. Stays put when an error appears.
  6. Counter (optional).field__counter, caption, --color-fg-subtle, end-aligned beside the help in a .cluster--between row. data-over turns it sorrel and semibold.

Spacing

  • Between the parts of one field: --space-1 (4px), from .field's gap. Don't add margins to the help or message; the search dialog's inline margin-top was drift.
  • Between fields in a form: --space-6 (24px, .form). Between the two fields of a .field-row: --space-4 (16px). The enquiry dialog tightens its stack to --space-5 (20px).
  • Help beside counter: --space-3 (12px) minimum, from .cluster; the counter wraps below the help rather than overlap it.

Sizes

The field itself has one size: label --text-label (14px medium), help --text-body-sm (14px), counter --text-caption (12px). It follows its control's size (.input--lg on the sign-in, register and password screens) without changing its own text or spacing.

The sign-in email (large, 52px control) and the audit log's "Target" (medium, 44px). The label and gap are the same.

  • Invalid appears after submit (with the error summary) or when leaving a field that was already submitted once, never while someone is still typing their first attempt. The value is kept.
  • Warning appears as soon as the value is known (on change or blur) and never blocks. It is mango and uses the ringed "!", so it can't be mistaken for an error.
  • Error and warning together: show only the error; the warning returns once the error is fixed.
  • Disabled fields keep their help, so the reason is visible ("Locked while our team reviews it"). Prefer read-only or a read-only value when the content still matters.
  • Busy (form submitting) puts controls in readonly, not disabled, so values stay readable and focus isn't lost.

Responsive behaviour

  • A field is always the full width of its column; forms cap at 40rem (.form) so lines stay readable on wide screens.
  • From 36rem, .field-row puts two short fields side by side (Event date and Guests; Event area and Postal code). Below 36rem they stack.
  • The help-and-counter row wraps: on a 320px phone a long help line takes the full width and the counter drops beneath it, end-aligned.
  • In the operator toolbar (.toolbar) fields are at least 10rem wide and wrap to new lines, with Apply staying at the end.
  • Labels, help and messages wrap; nothing truncates. Long words (email addresses in help) break with overflow-wrap.

Theming

The field reads semantic tokens only: --color-fg-default (label), --color-fg-subtle (optional marker, counter), --color-fg-muted (help), --color-danger-fg (error, over-limit counter) and --color-warning-fg (warning). The control's own tokens (--field-bg, --field-border, --field-fg) live on the text field.

In dark, help becomes stone-350, errors sorrel-300 and warnings mango-300; all stay above 4.5:1 on the stone-950 page and the stone-850 dialog surface. prefers-contrast: more lifts muted and subtle text a step automatically.

Accessibility

Role and pattern

Native labelling: <label for> pointing at the control's id, and aria-describedby listing the message, then help, then counter ids. Errors set aria-invalid="true" on the control. Required fields use required; there are no asterisks. See the W3C forms tutorial and WCAG 3.3.1.

Keyboard

KeyAction
Tab / Shift+TabMoves between controls. The label, help, message and counter are not tab stops.
Click or tap the labelFocuses the control (a bigger target than the control alone).
Enter on an error-summary linkMoves focus to this field's control, which then reads its label, error and help.

Focus

The ring sits on the control, not the field. After a failed submit, focus goes to the error summary, not the first field, so the count of problems is heard first.

Labelling

The label is a sibling of the control, not its parent. A <label class="field"> wrapping the help and error (279 mock fields) puts all that text into the accessible name, so "Business name" would be read as "Business name Enter a business name of 2 to 80 characters 2–80 characters…" and then again as the description. "(optional)" stays inside the label on purpose. The error's icon is CSS-generated and must not be read aloud (see Sources). A counter isn't a live region on every keystroke; a visually hidden polite status says "143 characters too many" once typing pauses past the limit.

Motion

Messages appear without animation, so the layout shift is immediate and short. The control's border transitions over --duration-fast; reduced motion zeroes it.

Touch

The label is part of the target (tapping it focuses the control), and every control is at least 44px tall. Help and counter text are not interactive.

Content

  • Labels are short nouns in sentence case, without colons: "Event date", "Guests", "Business name", "Name on the certificate".
  • Help gives the rule or an example, not an instruction to fill the field in: "An area like Scarborough, or a postal code like M1B 2K3".
  • Errors say what to do, name the limit, and repeat in the summary word for word: "Enter a whole number of guests from 1 to 5,000", "Write at least 50 characters (35 so far)". Never "Invalid input".
  • Warnings say what is unusual, without blame: "This caterer usually serves 20–300 guests".
  • Counters: "35 / 2,000" with a thin space around the slash and a thousands separator. The help states the range: "50–2,000 characters".
  • Help must match the real rule. The dish dialog says "Up to 60 characters" over a field that allows 80.
