Description list

Description lists pair a label with a value: how many guests a caterer serves, which areas they cover, what an enquiry asks for, what a food handler certificate says. Seven layouts share one rule: the label is quiet, the value is what people came to read.

Overview

Use a description list whenever the screen shows named facts about one thing. Every layout below is a real <dl>, so screen readers announce "description list" and pair each term with its value.

  • Facts (.facts): the caterer page's short, large facts — "Serves 20–300 guests" and the occasions — above the menu on phones and in the enquiry panel from 62rem.
  • Areas served (.regions): a region as the term, its municipalities as the value: "City of Toronto — Scarborough, East York, North York".
  • Record (.kv): account details and operator records — a label column, hairline rows, and room for a status or a small action at the end of each value.
  • Enquiry summary (.enquiry-summary): the four things a caterer needs to answer — event date, guests, area, occasion — in a sunken well at the top of every thread, with the original message.
  • Certificate (.certificate): the food handler certificate as the caterer entered it. It is the caterer's own statement; Sweet Hand does not certify kitchens.
  • Change review (.diff-old, .diff-new, .changed-flag): what a caterer changed, for the operator who approves or reverts it.
  • Plain (.dl): the base two-column list from the kit, for anything short that fits none of the above.

Don't use a description list for many records of the same shape — that is a table or list rows — or for a sequence of events, which is a timeline. Values the person can edit live in a form opened from an "Edit details" button, never inline in the list.

Anatomy

  1. Term<dt>: a noun in sentence case, --text-label in --color-fg-subtle (--color-fg-muted in .dl).
  2. Value<dd>: body text, or body-large in .facts and .regions. Wraps; long email addresses and certificate numbers break anywhere.
  3. Trailing status or action (optional, .kv)A status label or a small button pushed to the end of the value ("Verified", "Change password").
  4. Divider or containerHairline rows in .kv; a sunken well in .enquiry-summary; a hairline box in .certificate; nothing in .facts and .regions.

Change review

When a caterer edits a published page, operators see the old value struck through in --color-fg-muted and the new value highlighted on --color-warning-bg. A visible label ("Was" / "Now", "Current name" / "Requested name") always says which is which, because strike-through and highlight are not announced. .changed-flag marks anything changed since the last review.

Sizes

Each layout has one size; the layouts themselves are the scale. .facts and .regions set values at --text-body-lg for browsing customers; .kv, .enquiry-summary, .certificate and .dl use body text for working screens.

States

Description lists are not interactive, so they have no hover, focus, active or disabled state; buttons inside a value keep their own (see button). What changes is the data: loading, a missing value, a long value, a changed value and the certificate's date.

  • Loading: skeletons replace terms and values inside the same layout; the container is aria-hidden="true" and one visually hidden status announces the load.
  • Missing: on the caterer's own and operator screens say so plainly in .text-muted ("Not added", "No file uploaded"). On the public page leave the pair out; never show "N/A" to customers.
  • Long: values wrap. .certificate dd breaks anywhere so long numbers and file names never overflow; give long email addresses in .kv the same treatment.

Responsive behaviour

  • Below sm (36rem): .kv is one column — term above value, a hairline under each value. .enquiry-summary is two columns with the message full width. .regions is one column.
  • sm (36rem): .kv gains its 12rem term column with the hairline running under both cells.
  • md (48rem): .enquiry-summary becomes four columns in one row; .regions becomes two columns.
  • lg (62rem): on the caterer page .facts moves from the content column (.until-lg) into the sticky enquiry panel (.only-lg) above "Send an enquiry". The markup is repeated, not moved; only one copy is ever displayed.
  • .facts, .certificate and .dl keep their layout at every width; the certificate's term column is as wide as "Issued by", so it fits at 320px.

Theming

No component tokens: every layout reads semantic tokens. Terms use --color-fg-subtle (or --color-fg-muted in .dl), values inherit --color-fg-default, dividers and the certificate box use --color-border-default, the enquiry well uses --color-bg-surface-sunken, and change review uses --color-fg-muted (old), --color-warning-bg (new) and --color-warning-fg (flag).

In dark the well becomes --palette-stone-900 on the stone-950 canvas and the new-value highlight a deep mango, with the text staying --color-fg-default above 4.5:1. The certificate border stays a hairline in both themes; it is the only bordered list, so it must not gain a shadow.

Accessibility

Role and pattern

Native <dl> with <dt>/<dd> pairs. HTML allows one wrapping <div> per pair, which .facts, .regions and .enquiry-summary use for layout; .kv, .certificate and .dl need the pairs as direct children. There is no APG pattern; follow the HTML dl element. Each list sits under a heading ("Your details", "Areas served", "Food handler certificate") so it can be found by heading navigation.

Keyboard

KeyAction
TabSkips the list and stops only on controls inside values ("Change password", the certificate file) in reading order.
Enter, SpaceActivate those controls; there is nothing to activate on a term or value.

Focus

The list takes no focus. Buttons inside .kv values use the shared ring; the hairline row is tall enough that the 3px offset ring never overlaps the next row.

Labelling

The term is the label; don't repeat it in the value where avoidable. Change review must name old and new in text (the term, or "Was" / "Now"), and should mark them up as <del> and <ins>; strike-through and highlight alone are invisible to screen readers. Dates go in <time datetime>.

Motion

None. Description lists never animate; loading skeletons stop shimmering under reduced motion.

Touch

Only the controls inside values are targets. Small buttons ("Change password", the certificate file) grow to 44px below 48rem (L2-065.1) and are 36px from 48rem, with at least 8px clear inside the row padding.

Content

  • Terms are one or two nouns in sentence case, no colon: "Guests", "Occasions", "Issued by", "Event date", "Requested name".
  • Values are as the person wrote them, and specific: "Serves 20–300 guests" with an en dash; occasions from the fixed list; areas named by municipality or district ("Scarborough, East York, North York") under their region ("City of Toronto", "Durham"), never a street address.
  • Dates: full on detail screens ("Saturday 21 November 2026"), short in rows and records ("Thu 8 Oct", "14 Mar 2029"); times "7:15 p.m."; all in Toronto time.
  • Certificates always carry the caption "<Name>’s own statement; Sweet Hand doesn’t certify kitchens." Never write "verified kitchen", "approved by Sweet Hand" or "certified" about a caterer.
  • Private values (phone, email) carry a lock note saying who can see them: "Private until you share it in a thread", "Only operators and the caterer see these".
