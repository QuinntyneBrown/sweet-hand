Form layout

Form layout arranges fields into one calm column: fieldsets with legends, paired fields in a row, an error summary that links to each problem, and either a submit button or an autosave status. Sweet Hand has two kinds of form and they never mix.

Overview

Form layout is the set of containers around form fields: the column, groups, rows, the actions bar, the error summary and the save status. It decides spacing and order; the fields decide everything inside a field.

Sweet Hand has two kinds of form:

  • Submit forms do one thing when a button is pressed: create an account, sign in, send an enquiry, save a certificate, add a dish, record a breach. They end in a primary button, show a busy state while sending, and show an error summary if the server or the client finds problems.
  • Autosave forms are the caterer's profile editor (business details, cuisines and areas, guests and occasions). Every change saves on its own after 2 seconds or on blur (L2-038.1). There is no Save button; a save status under the page title says "Saving…", "Saved" or "Not saved: fix 2 things below", and the page ends with a quiet "Done" link back to the overview.

Use a dialog for a short form that belongs to something on the page (enquiry, report, dish, review). Use a full page for anything longer or anything people return to. Never place an inline form inside a page's content to edit something already shown; button-triggered editing opens a dialog (AGENTS.md).

Anatomy

  1. Error summary.form-summary: heading with the count, one link per problem. Only after a failed submit or save.
  2. FieldA form field: label, control, help, error.
  3. Field row.field-row: two short related fields side by side from 36rem.
  4. Actions.form-actions: the primary button (and a save status) under the last field.
  5. Column.form: a flex column, --space-6 between blocks, 40rem maximum width.

Variants

Groups: fieldset and legend

A <fieldset> groups fields that answer one question; its <legend> is the question. In the profile editor the legend holds the section heading (<legend><h2>Guests</h2></legend>) so the group and the outline agree. Fieldsets lose the browser border and padding.

Sticky actions

.form-actions--sticky pins the actions to the bottom of the viewport on a long form, above the home indicator (env(safe-area-inset-bottom)), with a hairline top border. No mock needs it yet: Sweet Hand's long forms autosave. Use it only for a long submit form on phones.

Filter toolbar

.toolbar lines up a few filter fields and an Apply button on one wrapping row, bottoms aligned. It is a small <form> with an aria-label, used on operator pages.

From pages/admin-metrics. Fields keep a 10rem minimum and wrap.

In a dialog

The enquiry form is a dialog that fills the screen below 48rem; the summary sits at the top of the dialog body and the footer holds Cancel and "Send enquiry".

Sizes

Forms have three widths, set by their container, never by the fields:

  • Auth (.auth, 28rem): sign in, create account, reset password. Large inputs (.input--lg, 52px) and a full-width large primary.
  • Page form (.form, 40rem): the profile editor and certificate. Medium (44px) inputs.
  • Dialog form (.dialog__panel--form, 40rem; default panel 32rem): enquiry, dish, report, breach.

Gaps: --space-6 between blocks in .form; the auth and dialog forms in the mocks use --space-5 between fields (set inline). A .form--compact modifier is proposed to replace the inline gap.

How each state behaves

  • Submitting (pages/register/submitting, pages/sign-in/submitting): fields become readonly (not disabled, so values stay readable and are still sent), the primary gets aria-busy="true" and ignores further presses, Cancel stays available in dialogs.
  • Invalid: validation runs on submit (novalidate plus our own messages, and the same rules on the server, L2-022.6). The summary appears above the form with role="alert" and tabindex="-1" and takes focus; every field keeps its value and shows its own error. An error clears as soon as its field is fixed; the summary refreshes on the next submit.
  • Autosave invalid: a field that breaks a rule is not saved; the status says "Not saved: fix 2 things below" and the same summary appears. Valid fields keep saving.
  • Saved: the status shows "Saved" with the time when it helps ("Saved at 10:14 a.m. · live on your page within a minute").
  • Failed (network or server): submit forms show a danger alert above the actions and keep every value; autosave shows a danger status and retries on the next change.
  • Read-only (profile under review): the form is replaced by a description list and an alert explaining why, not by disabled fields.

Responsive behaviour

  • Below 36rem everything is one column, including .field-row; buttons in auth forms are full width (.btn--block).
  • From 36rem .field-row splits into two equal columns (--space-4 gap). Never three: date, guests and postal code would truncate.
  • Below 48rem the enquiry dialog fills the screen (.dialog--full) and its footer sticks to the bottom; other dialogs dock to the bottom edge.
  • From 62rem the profile editor gains the side navigation and, from 75rem, the live preview; the form column stays 40rem wide.
  • .toolbar wraps fields onto new lines with a 10rem minimum each; Apply wraps with them.
  • .form-actions--sticky pads by env(safe-area-inset-bottom); when the on-screen keyboard is open the focused field must stay visible above it (WCAG 2.4.11).

Theming

Form layout is mostly space. The colours it owns: .form-summary uses --color-danger-bg with --color-danger-fg text and links (links inherit the colour, underlined); .form-actions--sticky uses --color-bg-canvas with a --color-border-default top edge; the save status uses --color-fg-muted, --color-success-fg and --color-danger-fg. In dark the summary becomes deep sorrel (--palette-sorrel-950) with light sorrel text. There are no component tokens.

Accessibility

Role and pattern

A <form> named by the page heading (aria-labelledby="page-title") or an aria-label becomes a form landmark. Groups are <fieldset>/<legend>. The error summary follows the ARIA21 and error identification guidance: identify each error in text and link to the field.

Keyboard

KeyAction
Tab / Shift+TabMoves through fields in visual order: left then right in a field row, top to bottom otherwise.
Enter in a text fieldSubmit forms: submits. Autosave forms: saves the field (as on blur); never navigates away.
Enter on a summary linkMoves focus into the field it names.
EscIn a dialog form, closes the dialog (same as Cancel); nothing is sent.

Focus

On a failed submit, focus goes to the summary, never to the first field, so screen-reader users hear how many problems there are. Sticky actions must not cover the focused field (WCAG 2.4.11); scroll padding equals their height.

Labelling

  • The summary heading has an id and the summary is aria-labelledby it.
  • Field errors are referenced by aria-describedby (error first, then help) and the field gets aria-invalid="true".
  • The save status is role="status" (polite). Busy buttons keep their label.
  • Optional fields say "(optional)"; required ones carry required and no asterisk.

Motion

The saving dot pulses over --duration-loop; reduced motion stops it and the word "Saving…" carries the state. Focus moving to the summary does not animate a scroll under reduced motion.

Touch

Every control is at least 44px tall; the space between fields (--space-5/--space-6) keeps neighbouring targets well over 8px apart. Fields declare inputmode, type and autocomplete so phones show the right keyboard (L2-065.2).

Content

  • Summary heading: "Fix {n} thing(s) to {goal}": "Fix 4 things to send your enquiry", "Fix 1 thing to save", "Fix 2 things so we can save". For uploads, name the result: "2 photos weren’t added".
  • Summary items repeat the field's own error, word for word, and link to it.
  • Save status: "All changes saved", "Saving…", "Saved at 10:14 a.m.", "Not saved: fix 2 things below". Times in Toronto time, "a.m."/"p.m.".
  • Legends are nouns ("Guests", "Occasions", "Areas you serve"); help lines state the rule with numbers ("Whole numbers from 1 to 5,000").
  • The page form's button says what it saves ("Save certificate"); a dialog's says what it does ("Send enquiry", "Add dish", "Send report").
  • Reassure when nothing was lost: "Your choices are safe. Try again in a moment."
