Tabs

Tabs switch between panels of one thing without leaving the page, marked by a pepper underline. Sweet Hand rarely needs them: no mock uses tabs, and list filters use the lighter segmented control instead.

Overview

.tabs is a row of .tab buttons over a hairline. The selected tab is ink and semibold with a 2px pepper underline: pepper because a selected tab is "you are here".

Where the mocks use tabs: nowhere. The patterns that look like tabs are something else:

  • Status filters on lists (Inbox "All 4 · Open 1 · Replied 1 · Declined 1 · Closed 1", caterer Enquiries, the operator queue "All 7 · Profiles 2 · Name changes 1…", Caterers "All 68 · Draft 3…", Reviews "Held 2 · Hidden 2") use the segmented control (.segmented): links that change the URL and filter the same list, current in pepper text, no underline, no panels. That is navigation, so it is <ul> of links with aria-current="page", not a tablist.
  • Long records such as the operator's caterer record (Owner, Profile, Food handler certificate, Activity, Status history) and the public caterer page (Menu, Areas served, Reviews) are stacked sections with headings. Operators scan them top to bottom; hiding the certificate behind a tab would make an expired one easy to miss.
  • Work-area sections use the side navigation.

Use tabs only when one object has two to five views that people switch between, each view is long enough that stacking would bury the others, and nobody needs to see two views at once. The examples below borrow the operator caterer record's section names to show the component; they are not a design decision for that page.

Anatomy

  1. Selected indicator2px (--border-width-thick) --color-accent bar over the hairline, top corners --radius-xs.
  2. Tab.tab: label in --text-label at 16px, --color-fg-muted; 44px tall, --space-3 padding.
  3. Count (optional)A badge: .badge--count only for something that needs action ("1 open report"); totals stay plain text in the label.
  4. Track.tabs: flex row, --space-1 gap, 1px --color-border-default bottom edge; scrolls sideways when it overflows.

Variants

Panel tabs (APG, automatic activation)

Buttons with role="tab" inside role="tablist", each controlling a role="tabpanel". Arrow keys move and select at once (automatic activation), which is right when panels are already loaded. This example works: click or use the arrow keys.

Link tabs (navigation)

When each view has its own URL, the row is navigation: links in a <nav>, current one aria-current="page", no tab roles, no arrow keys. .tab styles a as well as button. Prefer the segmented control for filters of one list; use link tabs for sibling pages of one object.

With counts, scrolling

Constrained to 20rem to show overflow: the row scrolls sideways inside itself with the scrollbar hidden; the page never scrolls. (The real queue uses the segmented control, which wraps instead.)

Sizes

Tabs have one size: 44px tall with 16px labels, so they meet the phone target without a compact variant. A denser row would need the segmented control, which is plain text.

States

Hover and focus are forced with data-state; selected uses aria-selected="true" (panel tabs) or aria-current="page" (link tabs); disabled uses disabled or aria-disabled="true".

Both themes

  • Loading a panel shows a skeleton inside the panel; the tab row never shows a spinner.
  • Disabled tabs are rare: remove a tab that can never apply; disable only one that will apply later and say why in the panel area.

Responsive behaviour

  • The row never wraps. When the tabs are wider than the container it scrolls sideways inside itself (overflow-x: auto, scrollbar hidden), so the page never scrolls at 320px. Keep labels short so four tabs fit at 360px; if they don't, the content wants the segmented control (which wraps) or stacked sections.
  • Scroll the selected tab into view on load and on arrow-key moves (scrollIntoView({ inline: "nearest" })).
  • Sizes are the same at every breakpoint. From 62rem tabs sit in the main column of a .work-layout, never beside the side nav.

Theming

Tabs read --color-fg-muted (label), --color-fg-default (hover and selected label), --color-border-strong (hover underline), --color-accent (selected underline), --color-border-default (track) and --color-fg-disabled. In dark the selected underline lifts to --palette-pepper-300. In forced-colours mode the selected tab is also underlined in text, because the bar may disappear. No component tokens.

Accessibility

Role and pattern

Panel tabs follow the APG Tabs pattern with automatic activation: role="tablist" with an aria-label, role="tab" with aria-selected and aria-controls, role="tabpanel" with aria-labelledby and tabindex="0". Use manual activation (arrows move, Enter selects) only if a panel has to load from the network. Link tabs are a <nav> of links with aria-current="page" and no tab roles.

Focus

Roving tabindex: the selected tab is 0, the others -1. The shared ring draws around the focused tab with the usual 3px offset, clear of the pepper bar.

Labelling

  • The tablist names the object: "Pelau House record". Tab labels name the view.
  • Counts inside a tab are part of its name: a total as plain text ("All 7"), an action count as a badge with an aria-label ("2 open reports").

Selected is shown three ways: weight, colour and the bar. Disabled labels are exempt from contrast minimums.

Motion

The underline colour fades over --duration-fast; it does not slide between tabs. Panels swap instantly.

Touch

Each tab is 44px tall and at least 44px wide in practice, with --space-1 between tabs plus their own padding. The row scrolls by swipe.

Content

  • One or two words per tab, nouns, sentence case: "Profile", "Certificate", "Status history".
  • Don't repeat the object in every tab ("Caterer profile", "Caterer certificate").
  • Counts follow the label with a space: "All 7", "Profiles 2". Write them one way across a row (the mocks' segmented rows mixed plain numbers and caption-styled counts).
  • Never use a tab label as an instruction ("Click to see reviews").

Code

// Automatic activation: arrows move focus and select.
tablist.addEventListener("keydown", (e) => {
  const tabs = [...tablist.querySelectorAll('[role="tab"]:not([disabled])')];
  const i = tabs.indexOf(document.activeElement);
  const next = { ArrowRight: i + 1, ArrowLeft: i - 1, Home: 0, End: tabs.length - 1 }[e.key];
  if (next === undefined) return;
  e.preventDefault();
  select(tabs[(next + tabs.length) % tabs.length]);   // sets aria-selected, tabindex, hidden; focuses the tab
});

Sources

No mock uses .tabs; it comes from the base kit. The related patterns come from:

  • pages/inbox/default (segmented status filter with counts)
  • pages/dashboard-enquiries/default (segmented, caterer side)
  • pages/admin-queue/default (segmented by kind)
  • pages/admin-caterers/default, pages/admin-reviews/default (segmented by status)
  • pages/admin-caterer/default (stacked sections instead of tabs)

Drift fixed during extraction: the kit's .tab styled only aria-selected; the system also styles aria-current="page" for link tabs and adds a disabled state. Segmented rows wrote counts two ways (pages/inbox wraps them in .filter-list__count; queue, caterers and reviews write plain "All 6"), and the queue's "Held reviews 1" sits in the filter row but links to a different page; both belong to the segmented control and are reported there.
