Inline message

The small lines of text that sit right next to what they are about: help under a field, an error that says how to fix it, a warning that does not block, and the quiet "Saving…" / "Saved" beside a caterer's profile. Each is tied to its control with aria-describedby or announced through a live region.

Overview

Inline messages are the lowest-level feedback on Sweet Hand: one line of small text, a glyph or dot, and a colour that is never the only signal. They live inside the layout, never over it.

  • Help (.field__help): what the field needs before anyone types. "2–80 characters. A new name goes live after our team checks it."
  • Error (.field__error): what is wrong and how to fix it, after a submit. "Enter a business name of 2 to 80 characters". Blocks the save.
  • Warning (.field__warning): something worth knowing that does not block. "Sweet Hand currently serves Toronto and the GTA", "This caterer usually serves 20–300 guests".
  • Inline status (.inline-status, --success, --danger): the result of an action, beside the action. "Contact details shared".
  • Save status (.save-status, --saved, --error): the autosave indicator in a dashboard page intro: "Saving…" with a pulsing .dot, "Saved", "Not saved: fix 2 things below".

When the message is about the whole page or needs an action, use an alert or banner. When it confirms something that happened elsewhere or will disappear, use a toast. A list of every error on submit is the error summary (.form-summary, see Form layout); inline errors repeat each item next to its field. The character counter (.field__counter) belongs to the form field but follows the same rules.

Anatomy

  1. Save status.save-status: 16px icon or 8px .dot + text, --text-body-sm, 44px tall so it never shifts the intro. Always present, with role="status".
  2. Invalid controlaria-invalid="true" gives the field a 2px danger edge; aria-describedby lists the error first, then help, then counter.
  3. Error.field__error: warning-sign glyph + text in --color-danger-fg, directly under the control.
  4. Help.field__help: muted, stays visible while there is an error, so the rule is still on screen.

Responsive behaviour

  • Messages take the field's width and wrap; the glyph stays aligned with the first line (align-items: flex-start).
  • Help and counter share a row (.cluster--between); below about 20rem the counter wraps under the help, right-aligned.
  • The save status keeps a 44px minimum height so "Saving…" → "Saved" never moves the page; in the dashboard intro it wraps under the status label on phones.
  • No breakpoint hides a message or moves it away from its control.

Theming

Each message reads one foreground role: --color-fg-muted (help, neutral status), --color-danger-fg (error, failed), --color-warning-fg (warning), --color-success-fg (saved, done), --color-fg-subtle (counter). There are no backgrounds: inline messages sit on whatever surface the field is on (canvas, card, dialog), so every foreground is checked against canvas, surface and raised surface. Dark lightens each foreground to keep 4.5:1. The pulsing dot uses currentColor.

Accessibility

Role and pattern

Field messages are plain text tied to their control with aria-describedby (WCAG 1.3.1, 3.3.1, 3.3.3). The order in the attribute is the reading order: error, help, counter. Status lines that change after load are live regions (role="status", polite) that exist in the DOM before their text changes. See the APG names and descriptions practice.

Keyboard

KeyAction
TabMessages are never focusable; focusing the control reads its label, then the described-by messages.
Enter on a summary linkMoves focus to the field, whose error is read next.

Focus

After an invalid submit, focus goes to the error summary (role="alert", tabindex="-1"), not to an inline error. Fixing a field removes its error and aria-invalid as the person types (re-validate on input), silently.

Labelling and live regions

  • Errors start with a glyph and are coloured, but the words carry the meaning; the control also gets aria-invalid="true". They are not live regions themselves: the summary announces them.
  • Warnings that appear while typing (postal code out of area) use role="status"; warnings present on load are plain text.
  • Save status has role="status" so "Saving…", "Saved" and "Not saved" are each announced once. It is not repeated in a toast.
  • Inline status replaces the button it reports on when the action is one-way, and returns focus to the nearest remaining control.

Motion

The .dot--pulse fades between full and 35% opacity over --duration-loop. It is decorative (the text says "Saving…"), so reduced motion stops it and leaves a solid dot.

Touch

Not interactive. Inline messages never contain the only route to an action; links inside them ("Try again") meet the 24px minimum with spacing.

Content

  • Errors say what to do, in the imperative, with the limit: "Enter a business name of 2 to 80 characters", "Write at least 50 characters (35 so far)", "Keep your reply under 2,000 characters. It’s 2,143 now." Never "Invalid input" or "Error". No trailing period on single-clause errors.
  • Help states the rule and who sees what: "2–80 characters. A new name goes live after our team checks it.", "Pelau House gets an email. Links show as plain text."
  • Warnings describe the fact, not a fault, and address the reader correctly: to a customer, "Pelau House usually serves 20–300 guests"; to the caterer, "You don’t list Downtown Toronto as an area you serve".
  • Save status: "Saving…", "Saved", "Saved at 10:14 a.m. · live on your page within a minute", "Not saved: fix 2 things below". Times lowercase with periods.
  • Use the ellipsis character (…) for in-progress text.

Drift fixed during extraction:

  • Error placement varied: before help (profile-details/invalid), after help and counter (dialogs/review/invalid), replacing help (thread/invalid). The order is now control → error → help → counter.
  • Four mocks showed "All changes saved" without --saved (neutral grey), 27 showed "Saved" in green; it is "Saved" with --saved everywhere.
  • dashboard-enquiry showed the caterer "This caterer doesn’t list Downtown Toronto…"; the caterer-side wording is "You don’t list…". The enquiry warning "This caterer usually serves 20–300 guests" duplicated the help "Pelau House serves 20–300" beside it; one line, naming the caterer, remains.
  • "Contact details shared" used .private-note with a success icon; it is an .inline-status--success. .inline-status was otherwise unused.
  • An over-limit counter was coloured with an inline style; it uses data-over.
  • The .field__error glyph is generated text ("⚠") that some screen readers announce and some platforms draw as a colour emoji; an alt-text-empty, text-presentation form is proposed.
