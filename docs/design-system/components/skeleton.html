Skeleton

Skeletons draw the shape of what is coming — round photos, names, rows — in quiet stone, so a page that is loading already looks like itself and nothing jumps when the content arrives.

WCAG 2.2 AAStatus: stable.skeletonaria-busy

Overview

A skeleton is a block of --color-bg-subtle with a slow shimmer, cut to the size of the content it stands in for. Sweet Hand pages load as skeletons of themselves: the listing shows grey circles in the same grid as the caterer photos, the inbox shows rows with a circle and two lines, the operator queue shows its rows.

Rules that make skeletons work here:

  • Same box, same place. The skeleton occupies exactly the space of the final content: a 17.5rem circle where the round caterer photo goes, a 48px circle where the inbox photo goes. When content arrives, nothing moves (WCAG-friendly and no layout shift).
  • Only what is unknown. The header, the page title, the filter names and the tabs are known before the data, so they render for real. Only counts, names and photos are skeletons ("filter names are known, counts are not yet").
  • Only after 300ms. Fast loads go straight from blank to content; skeletons appear only if the wait passes 300ms.

Choose something else when:

  • There is no layout to preview (the next photo in the viewer, a postal code lookup): a spinner.
  • The amount is measurable (an upload): a progress bar.
  • An action is running on existing content (saving, sending): the button's busy state; do not turn content back into skeletons.
  • The load failed or returned nothing: an empty state.

Anatomy

  1. Busy containerThe real list (<ul class="caterer-grid">) with aria-busy="true"; a nearby role="status" says "Loading caterers".
  2. Circle.skeleton--circle filling the real .photo box, so the round photo lands in exactly the same place.
  3. Name line.skeleton--text, 0.9em high with 0.3em above and below, so it matches one line of text; 9rem wide on cards.
  4. Meta lineA second, shorter .skeleton--text (6rem): the "Jamaican · Pickering" line. Last lines are shorter so the block reads as text.

Variants

Shapes

Four primitives. Width comes from the context (a modifier on the composed row, or the column); height and radius from the shape.

--title (1.5em, 40%), --text (0.9em; the last in a group is 60%), --circle (photos, avatars), --rect (buttons, inputs, charts; --radius-md).
HTML
<span class="skeleton skeleton--title"></span>
<span class="skeleton skeleton--text"></span>
<span class="skeleton skeleton--circle" style="width: 3rem; height: 3rem;"></span>
<span class="skeleton skeleton--rect" style="height: var(--control-height-lg);"></span>

Sizes

Skeletons have no size scale. Each one copies the box of the content it stands in for: --text scales with the surrounding font size (it is in em), circles fill the .photo or avatar box they sit in, and rects take the control height they replace (--control-height-sm/lg).

States

Skeletons are not interactive. Their states are about the loading lifecycle, and the real attribute is aria-busy on the container.

Both themes

  • Delayed: nothing (or the known parts only) for the first 300ms; then skeletons.
  • Loaded: skeletons are replaced in one swap, aria-busy is removed, and the status text changes to the result ("60 caterers", "4 enquiries · 1 unread"). Photos may keep loading inside their round boxes, showing --color-bg-photo until they arrive.
  • Failed: skeletons are replaced by an empty state in error tone in the same region; the page header, title and filters stay.
  • Paging (Load more, next page): existing rows stay; skeletons are appended below them only, never replacing what is already read.

Responsive behaviour

  • Skeletons live inside the real layout, so they follow it: the caterer grid is 1 column on xs, 2 from 36rem, 3 from 62rem; render enough skeleton cards to fill the first screen at each (3 on xs, 6 on sm and md, 9 from lg), not a fixed 24.
  • The inbox shows 4 skeleton rows on every size; from 62rem the thread column shows a large circle and one line where "Choose an enquiry to read it here" will be.
  • Operator queue rows use .queue-item--stack below 36rem, and so do their skeletons, so the stacked phone layout is previewed too.
  • Widths are percentages or min(…, 100%), never fixed widths wider than a 320px screen.

Theming

The skeleton reads --color-bg-subtle for its base and --color-bg-subtle-hover for the shimmer highlight, as a 90° gradient moved across a 400% background. In dark both are dark stone steps, one lighter than the other, so the sweep stays subtle. No component tokens; no pepper, no ink. A skeleton should be the quietest thing on the screen.

.skeleton { background: linear-gradient(90deg, var(--color-bg-subtle) 25%, var(--color-bg-subtle-hover) 37%, var(--color-bg-subtle) 63%);
            background-size: 400% 100%; animation: shimmer var(--duration-loop) var(--ease-standard) infinite; }

Accessibility

Role and pattern

Skeleton items are aria-hidden="true"; they mean nothing to a screen reader. The container being loaded keeps its real element and role (the <ul>, the <table> with its caption and column headers) and carries aria-busy="true". A role="status" element names what is loading ("Loading caterers", "Loading the review queue") and later announces the result. This follows the aria-busy definition and WCAG 4.1.3; the APG has no skeleton pattern.

Keyboard

KeyAction
TabSkips skeletons; nothing in them is focusable. Real controls on the page (filters, tabs, header links) work while the content loads.

Focus

Focus is never placed on a skeleton and never moved when content arrives. If focus was on a control that the loaded content replaces (a page link in pagination), it moves to the first result's heading or link.

Labelling

One status message per loading region, specific to it: "Loading your enquiries", "Loading audit entries". Do not label each skeleton item. Tables keep their real column headers and a caption ending in ", loading".

Contrast

Text on the shimmer highlight (if text ever sits on it)
Text on the skeleton base

Skeleton shapes are decorative and exempt from 1.4.11: they carry no information, and the status text says what is happening. They should be visible but faint; the base against the canvas is intentionally low contrast.

Motion

The shimmer is a decorative loop (--duration-loop, 1.4s). Under prefers-reduced-motion it stops and the skeleton is a flat --color-bg-subtle block (the reduced-motion column above). Status still comes through the live region, so nothing is lost. The shimmer never flashes: it is a soft brightness change well under the three-flashes threshold.

Touch

Nothing to touch. Skeleton rows are not links; the rows become tappable only when they are real.

Content

  • Skeletons carry no words. The status message does: "Loading caterers", "Loading your enquiries", "Loading the review queue", "Verifying your email…".
  • Render real text for everything known in advance: page titles ("Inbox"), filter names (Jamaican, Trinidadian & Tobagonian…), table headers, tab labels. Only counts and records are skeletons.
  • Never put "Loading…" in place of a caterer name or a count; use a text skeleton of the right width.
