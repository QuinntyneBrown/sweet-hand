# 0006 — Backend stack: NestJS on Node.js, PostgreSQL through Drizzle ORM, S3-compatible object storage

- Status: Accepted
- Date: 2026-10-11

## Context

The detailed designs in `docs/detailed-designs/` name an API, a background
worker, a database, a job queue and object storage with `<TO SUPPLY>`
technology. ADR 0001 fixed Node 22 and TypeScript for the frontend, and the
fake backend (ADR 0004) already runs on that runtime. L2-030 and L2-091 need a
persistent queue whose enqueue survives with the state change; L2-078 needs
opaque server-side sessions; L2-082 needs limits shared across API instances;
L2-060 AC2 and L2-073 constrain database permissions; L2-041 fixes image
processing; L2-075 and L2-090 fix Canadian regions and cross-region backups.

## Decision

- The backend is a NestJS application in `backend/` (planned, repository
  root), Node.js 22 and TypeScript. Two entry points share the application
  and domain modules: the `Sweet Hand API` (HTTP) and the
  `Sweet Hand background worker` (queued and scheduled jobs).
- PostgreSQL is the only stateful service in the first release. It holds the
  relational data, server-side sessions (opaque identifiers, hashed at rest,
  L2-078 AC1), rate-limit counters (L2-082), security-event counters
  (L2-084 AC3) and the job queue. No Redis or other cache or queue service
  until measurements show the need.
- The job queue is pg-boss (or an equivalent PostgreSQL-table queue). A
  command handler enqueues through the same database transaction as its
  state change, so both commit or neither does (L2-030 AC1, L2-091 AC1). The
  worker dequeues with retries and exponential backoff.
- Data access goes through Drizzle ORM (`drizzle-orm` on `node-postgres`).
  Migrations are generated by `drizzle-kit` and applied by an explicit
  command (`npm run db:migrate` in `backend/`), never on startup. The queue's
  schema is created by the same migrations; pg-boss runs with
  `migrate: false`.
- Database roles: `sweethand_migrate` owns the schema and runs migrations;
  `sweethand_app` serves the API and worker and has INSERT and SELECT only on
  the audit table (L2-060 AC2); `sweethand_retention` is used only by the
  retention job (L2-073) and is the only role with DELETE on the audit table.
- Files (photo originals and derivatives, certificates, exports) live in
  S3-compatible object storage behind an `ObjectStore` port. Originals stay
  in a private prefix; derivatives are served through the CDN.
- Image processing (L2-041) runs inside the background worker with `sharp`
  (libvips): content sniff, EXIF/XMP/IPTC removal, re-encoding to AVIF, WebP
  and JPEG at 400, 800, 1200 and 2000 px, never enlarging. Malware scanning
  stays an external service. Prebuilt `sharp` binaries do not decode HEIC
  (L2-041 AC1); how the worker image gains HEIC decoding is `<TO SUPPLY>`.
- Managed PostgreSQL and object storage run in a Canadian region.
  Point-in-time recovery backups and object-storage replicas go to a second
  Canadian region (L2-075, L2-090).
- Server rendering of `/caterers/{slug}` (L2-018 AC4) will use
  `@angular/ssr` on the same Node.js runtime; enabling it remains deferred
  (ADR 0001).
- Wire models stay in `frontend/projects/api/src/lib/models/` (one type per
  file, import-free). The backend imports them with `import type`, as the
  fake backend does. Moving them to a shared package is `<TO SUPPLY>`.
- Still `<TO SUPPLY>`, each for its own ADR: hosting provider, secret store,
  CDN, email provider, bot-protection provider, malware scanner, CI service,
  observability platform.

## Consequences

- One language and runtime across frontend, fake backend and backend;
  contributors need Node 22.12+ for `backend/` as well.
- Sessions, counters and the queue add one write per request to PostgreSQL;
  a later ADR may move them if measurements require it.
- Every design's `Sweet Hand API`, `background worker`, `database`,
  `Job queue` and `Object storage` slots take the names above; provider
  slots remain `<TO SUPPLY>`.
