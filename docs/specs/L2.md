# L2 - Detailed Requirements

**Product:** Sweet Hand
**Traces from:** `docs/specs/L1.md`
**Status:** Approved 2026-10-10
**Last updated:** 2026-10-12 (L2-110 to L2-136, the operator directory of places and events, added as a draft pending approval; L2-073 gains directory rows). 2026-10-11: L2-092 to L2-107, the pre-launch site, added as a draft pending approval; L2-073 gains launch list rows.

## Conventions used in this document

- **Viewport classes:** XS < 576px, SM ≥ 576px, MD ≥ 768px, LG ≥ 992px, XL ≥ 1200px (CSS pixel width). "Phone" means XS, "tablet" means SM–MD, "desktop" means LG–XL.
- **Time zone:** all dates and times are stored in UTC and shown in `America/Toronto`. "Today" means the current date in `America/Toronto`.
- **Published caterer:** a caterer profile with status `Published` (see L2-046). No other status appears to visitors or customers.
- **Visible within N seconds:** measured from when the triggering request is acknowledged to when an uncached request for the affected public page reflects the change.
- **Length limits** count Unicode characters after leading and trailing whitespace is trimmed.
- **Supported browsers:** the latest two stable versions of Chrome, Edge, Firefox and Safari (macOS and iOS), plus Samsung Internet (see L2-064).
- **Not found:** when a record does not exist *or* the requester is not authorised to see it, the platform returns HTTP 404 with the same body in both cases. It never reveals that a hidden record exists.

## L2-001: Listing shows only published caterers
**Traces to:** L1-001

The caterer listing must include every caterer whose profile status is `Published` and must exclude every other status (`Draft`, `Pending review`, `Changes requested`, `Suspended`, `Removed`).

**Acceptance Criteria:**
1. Given 3 caterers with status `Published` and 1 caterer in each of `Draft`, `Pending review`, `Changes requested`, `Suspended` and `Removed`, when a visitor opens the listing with no filters, then exactly the 3 published caterers appear and the result count reads "3 caterers".
2. Given a caterer in `Pending review`, when an operator approves the profile, then the caterer appears in the unfiltered listing within 60 seconds.
3. Given a published caterer, when an operator suspends the profile, then the caterer disappears from the listing within 60 seconds.
4. Given no published caterers match the current filters, when the listing loads, then an empty state appears that says "No caterers match these filters" with a "Clear filters" control, and no error status is returned.

---

## L2-002: Listing order and pagination
**Traces to:** L1-001

The listing must show 24 caterers per page. With no sort chosen by the user, caterers must appear in a pseudo-random order seeded by the current date, so that no caterer is permanently favoured and the order stays stable within a day.

**Acceptance Criteria:**
1. Given 60 published caterers, when a visitor opens the listing, then page 1 shows 24 caterers, page 2 shows 24 and page 3 shows 12.
2. Given 60 published caterers and a fixed date, when a visitor walks pages 1 to 3, then every caterer appears exactly once across the three pages.
3. Given the same filters on the same calendar date, when the listing is requested twice, then the order is identical both times.
4. Given the same filters on two different calendar dates, when the listing is requested once on each date, then the order differs (verified with at least 10 caterers).
5. Given a page number greater than the last page, or one that is zero, negative or not an integer, when the listing is requested, then the platform shows page 1 and does not return an error.

## L2-003: Listing state is kept in the URL
**Traces to:** L1-001

The active filters, search terms and page number must be stored in the URL query string. A listing URL must be shareable and bookmarkable, and must work with the browser Back button.

**Acceptance Criteria:**
1. Given a visitor applies the cuisine filter "Jamaican" and goes to page 2, when they copy the URL into a new browser session, then the listing opens with the "Jamaican" filter applied on page 2.
2. Given a visitor changes a filter, when they press the browser Back button, then the previous filter state and its results are restored.
3. Given the URL contains an unknown filter value (for example `cuisine=atlantis`), when the listing loads, then that value is ignored, all valid filters are still applied, and no error is shown.

## L2-004: Listing card content
**Traces to:** L1-002

Each listing card must show exactly four things: the caterer's cover photo, business name, primary cuisine and primary service area. It must show nothing else, including ratings, prices and contact details. The whole card must be a single link to the caterer page.

**Acceptance Criteria:**
1. Given a published caterer with cover photo P, name "Island Pot", primary cuisine "Jamaican" and primary area "Scarborough", when the listing renders, then that caterer's card shows P, "Island Pot", "Jamaican" and "Scarborough", and no other text.
2. Given a published caterer with reviews, when its card renders, then no rating, star icon or review count appears on the card.
3. Given a visitor activates any part of a card by click, tap or Enter key, when the action completes, then the browser navigates to that caterer's page.
4. Given a business name longer than the card width, when the card renders, then the name is cut off with an ellipsis after 2 lines and the full name is available to assistive technology.

---

## L2-005: Responsive listing grid
**Traces to:** L1-002

The listing must use a grid of cards whose column count depends on the viewport class. Photos are round (1:1) and must take up at least 60% of each card's height.

**Acceptance Criteria:**
1. Given viewport XS, when the listing renders, then cards appear in 1 column.
2. Given viewport SM or MD, when the listing renders, then cards appear in 2 columns.
3. Given viewport LG, when the listing renders, then cards appear in 3 columns.
4. Given viewport XL, when the listing renders, then cards appear in 3 columns, with the extra width going to white space around the grid.
5. Given any viewport class, when a card renders, then its photo is a 1:1 circle and fills at least 60% of the card's height.
6. Given a viewport 320px wide, when the listing renders, then the page does not scroll horizontally.

---

## L2-006: Listing image delivery
**Traces to:** L1-002

Listing photos must be delivered in sizes matched to the viewport and in modern formats. Photos below the fold must load lazily. Every image must have a text alternative.

**Acceptance Criteria:**
1. Given a card photo, when the listing HTML is inspected, then the image declares a `srcset` with at least widths 400, 800 and 1200 and a `sizes` attribute that matches the grid in L2-005.
2. Given a browser that supports AVIF or WebP, when a card photo is requested, then it is served in AVIF or WebP.
3. Given a listing page, when it first loads, then only images in the first viewport have eager loading and all others have `loading="lazy"`.
4. Given a card photo, when it renders, then its `alt` text is the caption the caterer entered for that photo (L2-042).
5. Given a photo has not loaded yet or fails to load, when the card renders, then a neutral placeholder of the same aspect ratio is shown and the layout does not shift.

## L2-007: Cuisine and island-of-origin taxonomy
**Traces to:** L1-003

The platform must keep a list of Caribbean cuisines (by island or country of origin) that operators manage. Each caterer must pick 1 to 5 cuisines and mark exactly one as primary. The initial list is: Antiguan & Barbudan, Bahamian, Barbadian (Bajan), Belizean, Cuban, Dominican (Dominica), Dominican (Dominican Republic), Grenadian, Guyanese, Haitian, Jamaican, Kittitian & Nevisian, Puerto Rican, St. Lucian, Surinamese, Trinidadian & Tobagonian, Vincentian, Pan-Caribbean.

**Acceptance Criteria:**
1. Given a newly installed platform, when the cuisine list is retrieved, then it contains exactly the 18 initial entries above, in alphabetical order.
2. Given a caterer editing their profile, when they save with 0 cuisines or more than 5, then the save is rejected with the message "Choose between 1 and 5 cuisines".
3. Given a caterer selects 3 cuisines, when they save without marking one as primary, then the save is rejected with the message "Mark one cuisine as primary".
4. Given an operator adds the cuisine "Caymanian", when a caterer next edits their profile, then "Caymanian" can be selected and the listing filter offers it.
5. Given an operator retires a cuisine that 2 published caterers use, when the retirement is saved, then the cuisine no longer appears as a filter option or new selection, those 2 caterers keep it on their pages, and the operator sees a warning naming the 2 caterers.

## L2-008: Filter listing by cuisine
**Traces to:** L1-003

A visitor must be able to filter the listing by one or more cuisines. If several are selected, a caterer matches when it offers *any* of them. Each option must show how many published caterers it matches when combined with the other active filters.

**Acceptance Criteria:**
1. Given caterers A (Jamaican), B (Haitian) and C (Jamaican, Trinidadian & Tobagonian), when a visitor selects "Jamaican", then A and C appear and B does not.
2. Given the same caterers, when a visitor selects "Haitian" and "Trinidadian & Tobagonian", then B and C appear.
3. Given the cuisine filter is open, when it renders, then each option shows the count of matching published caterers, and options with a count of 0 are shown but disabled.
4. Given a cuisine filter and an area filter are both active, when results load, then only caterers that match at least one selected cuisine *and* at least one selected area appear.
5. Given one or more cuisines are selected, when the visitor activates "Clear filters", then all cuisine and area filters are removed and the full listing appears.
6. Given a visitor changes the cuisine selection, when the results update, then the new results appear within 1 second at the 95th percentile on a broadband connection, with no full page reload.

## L2-009: Responsive filter controls
**Traces to:** L1-003

The filter controls must suit each viewport class.

**Acceptance Criteria:**
1. Given viewport XS or SM, when the listing renders, then filters sit behind a "Filters" button that shows the number of active filters, and activating it opens a full-height panel with a "Clear" button and a primary button that applies the filters and names the result count (for example "Show 2 caterers").
2. Given viewport MD, when the listing renders, then filters appear as a horizontal bar of dropdown controls above the grid.
3. Given viewport LG or XL, when the listing renders, then filters appear in a sidebar that stays visible to the left of the grid.
4. Given any viewport class, when filters are active, then each active filter appears as a removable chip above the results.

## L2-010: Service area model
**Traces to:** L1-004

The platform must keep a fixed list of service areas within Toronto and the GTA, grouped by region. Each caterer must pick at least 1 service area and mark exactly one as primary. The initial list is:

- **City of Toronto:** Downtown Toronto, East York, Etobicoke, North York, Scarborough, York
- **Peel:** Brampton, Caledon, Mississauga
- **York Region:** Aurora, East Gwillimbury, Georgina, King, Markham, Newmarket, Richmond Hill, Vaughan, Whitchurch-Stouffville
- **Durham:** Ajax, Brock, Clarington, Oshawa, Pickering, Scugog, Uxbridge, Whitby
- **Halton:** Burlington, Halton Hills, Milton, Oakville

**Acceptance Criteria:**
1. Given a newly installed platform, when the service area list is retrieved, then it contains exactly the 30 areas above, grouped under the 5 regions.
2. Given a caterer editing their profile, when they save with 0 service areas, then the save is rejected with the message "Choose at least one area you serve".
3. Given a caterer selects a whole region (for example "Peel"), when the selection is saved, then every area in that region is stored as selected.
4. Given a caterer selects 4 areas without marking one as primary, when they save, then the save is rejected with the message "Choose your primary area".

## L2-011: Filter listing by area
**Traces to:** L1-004

A visitor must be able to filter the listing by one or more service areas or whole regions. The area control must suggest matching areas as the visitor types.

**Acceptance Criteria:**
1. Given caterer A serves Scarborough and caterer B serves Mississauga, when a visitor filters by "Scarborough", then A appears and B does not.
2. Given a visitor filters by the region "City of Toronto", when results load, then every published caterer serving at least one area in the City of Toronto appears.
3. Given a visitor types "scar" in the area control, when suggestions appear, then "Scarborough" is suggested. Matching ignores case and accents and finds the typed text anywhere in the area name.
4. Given a visitor types text that matches no area, when suggestions would appear, then the control shows "No matching areas" and the active filters do not change.

## L2-012: Search by postal code
**Traces to:** L1-004

A visitor must be able to enter a Canadian postal code and see caterers that serve the area containing it. The platform must resolve the postal code's forward sortation area (FSA, the first 3 characters) to one of the service areas in L2-010. Only the FSA is used. The full postal code is never stored with any analytics or log entry.

**Acceptance Criteria:**
1. Given a visitor enters "M1B 2K3", when the search runs, then the listing filters to caterers serving Scarborough.
2. Given a visitor enters "m1b2k3" (lower case, no space), when the search runs, then the result is the same as for "M1B 2K3".
3. Given a visitor enters "M1B" (FSA only), when the search runs, then the listing filters to caterers serving Scarborough.
4. Given a visitor enters a code that is not a valid Canadian postal code format (for example "12345" or "MMM 1B1"), when they submit, then the message "Enter a valid postal code, like M5V 2T6" appears and the results do not change.
5. Given a visitor enters a valid postal code outside the service areas (for example "K1A 0B1"), when they submit, then the message "Sweet Hand currently serves Toronto and the GTA" appears and the results do not change.
6. Given a postal code search has run, when application logs and analytics records are inspected, then no value longer than the 3-character FSA has been stored.

## L2-013: Public access without an account
**Traces to:** L1-005

The listing, all filters and searches, and all caterer pages, including reviews, must be fully usable without signing in. The platform must ask a visitor to sign in only when they try to send an enquiry, leave a review, or open their account pages.

**Acceptance Criteria:**
1. Given a visitor who is not signed in, when they open the listing, apply filters, page through results and open 5 caterer pages, then no sign-in prompt, registration wall or modal appears.
2. Given a visitor who is not signed in, when they request a listing URL or caterer page URL, then the response is HTTP 200 with the full content.
3. Given a visitor who is not signed in, when they activate "Send an enquiry" on a caterer page, then they are taken to sign-in or registration, and after a successful sign-in they return to the enquiry form for that caterer (see L2-023).

## L2-014: Limits on public data
**Traces to:** L1-005

Public pages and the public API they use must expose only the fields needed for display. Caterer email addresses, phone numbers, food safety credentials, internal notes, unpublished content and record status must never appear in public responses.

**Acceptance Criteria:**
1. Given a published caterer with an account email, phone number and food handler certificate, when the public caterer page HTML and every public API response it uses are inspected, then none of those values appears.
2. Given a caterer in `Draft`, `Pending review`, `Changes requested`, `Suspended` or `Removed`, when a visitor requests that caterer's page URL or public API record, then the response is not found (HTTP 404, or HTTP 410 for `Removed` as defined in L2-018).
3. Given a published caterer who has saved edits that are still waiting for re-approval (L2-044), when the public page is requested, then it shows only the approved values.

## L2-015: Caterer page content
**Traces to:** L1-006

Each published caterer must have a page showing, in this order: a photo gallery, the business name, cuisines (primary first), a description, a summary of event sizes and occasions (L2-020, L2-021), menu or sample dishes, service areas grouped by region, reviews (L2-051), and a "Send an enquiry" button.

**Acceptance Criteria:**
1. Given a published caterer with 6 photos, a description, 2 cuisines, 8 menu items and 4 service areas, when the page renders, then all of these appear in the order listed above.
2. Given a caterer's description contains line breaks, when the page renders, then each blank-line-separated block is shown as a separate paragraph. Any HTML or markup in the description is shown as literal text and is never interpreted.
3. Given service areas in 2 regions, when the page renders, then the areas appear grouped under their region names.
4. Given any viewport class, when the visitor scrolls past the first "Send an enquiry" button, then a "Send an enquiry" button stays fixed in view (a sticky bottom bar on XS–MD; a sticky side panel on LG–XL).

## L2-016: Photo gallery
**Traces to:** L1-006

The caterer page gallery must show the caterer's photos in the order they set, starting with the cover photo. It must open a full-screen viewer that works with mouse, touch and keyboard.

**Acceptance Criteria:**
1. Given a caterer with photos ordered P1 (cover), P2, P3, when the page renders, then the gallery shows P1 first, then P2, then P3.
2. Given the visitor activates any gallery photo, when the viewer opens, then that photo is shown full-screen with its caption and a position indicator (for example "2 of 6").
3. Given the viewer is open, when the visitor presses Right Arrow or Left Arrow, or swipes left or right on a touch device, then the next or previous photo is shown.
4. Given the viewer is open, when the visitor presses Escape or activates the close button, then the viewer closes and focus returns to the photo that opened it.
5. Given the viewer is open, when the visitor presses Tab repeatedly, then focus stays inside the viewer.

## L2-017: Menu and sample dishes
**Traces to:** L1-006

The caterer page must list the caterer's menu items. Each item shows a name, an optional description, optional dietary tags and optional price guidance.

**Acceptance Criteria:**
1. Given a menu item with name "Curry goat", description "Slow-cooked with scotch bonnet", tags "Halal" and "Gluten-free", and price guidance "From $18 per person", when the page renders, then all four values are shown for that item.
2. Given a menu item with only a name, when the page renders, then only the name is shown, with no empty labels or placeholder text.
3. Given dietary tags, when they are displayed, then they come only from this fixed list: Vegetarian, Vegan, Gluten-free, Dairy-free, Halal, Contains nuts, Contains shellfish, Spicy.
4. Given a caterer with more than 12 menu items, when the page renders, then the first 12 are shown and a "Show all N dishes" control expands the rest without a page reload.

---

## L2-018: Caterer page URL and sharing
**Traces to:** L1-006

Each caterer page must have a stable, readable URL of the form `/caterers/{slug}`, where the slug comes from the business name. Pages must be rendered on the server and include metadata for search engines and link previews.

**Acceptance Criteria:**
1. Given a caterer named "Auntie Bev's Kitchen", when the profile is first published, then its URL is `/caterers/auntie-bevs-kitchen`.
2. Given a second caterer whose name gives the same slug, when it is published, then its URL gets a numeric suffix (`/caterers/auntie-bevs-kitchen-2`).
3. Given a caterer's business name change is approved, when a visitor requests the old URL, then the response is an HTTP 301 redirect to the new URL.
4. Given a published caterer page, when the HTML is fetched without running JavaScript, then it contains the business name, description and menu items. It also contains a `<title>`, a meta description, a canonical link and the Open Graph tags `og:title`, `og:description`, `og:image` (the cover photo) and `og:url`.
5. Given a caterer with status `Removed`, when its URL is requested, then the response is HTTP 410 with a page linking back to the listing. Given status `Suspended`, then the response is HTTP 404.
6. Given the platform is running, when `/sitemap.xml` is requested, then it lists the URLs of all published caterers and no others.

## L2-019: Responsive caterer page layout
**Traces to:** L1-006

The caterer page layout must suit each viewport class.

**Acceptance Criteria:**
1. Given viewport XS, when the caterer page renders, then the gallery is a swipeable carousel with full-width photos and all sections are stacked in one column.
2. Given viewport SM or MD, when the page renders, then the gallery shows a large lead photo with a strip of thumbnails beneath it, and sections are in one column.
3. Given viewport LG or XL, when the page renders, then the gallery shows a lead photo plus a grid of up to 4 thumbnails, and the content uses two columns: the main content, plus a side panel holding event sizes, occasions and the enquiry button.
4. Given any viewport 320px wide or wider, when the page renders, then there is no horizontal scrolling.

## L2-020: Event size range
**Traces to:** L1-007

Each caterer must state the minimum and maximum number of guests they cater for. Both are whole numbers from 1 to 5,000, and the minimum cannot be larger than the maximum. The caterer page must display the range.

**Acceptance Criteria:**
1. Given a caterer with a minimum of 20 and a maximum of 300, when the caterer page renders, then it shows "Serves 20–300 guests".
2. Given a caterer whose minimum equals their maximum (50), when the page renders, then it shows "Serves 50 guests".
3. Given a caterer enters a minimum of 400 and a maximum of 100, when they save, then the save is rejected with the message "Minimum guests can't be more than maximum guests".
4. Given a caterer enters 0, 5001, a negative number, a decimal or non-numeric text in either field, when they save, then the save is rejected with the message "Enter a whole number from 1 to 5,000".

---

## L2-021: Occasions
**Traces to:** L1-007

Each caterer must pick at least 1 occasion from a fixed list: Weddings, Birthdays, Corporate events, Funerals and repasts, Religious and cultural celebrations, Family gatherings, Private dinners, Community events. The caterer page must display the chosen occasions.

**Acceptance Criteria:**
1. Given a caterer selects "Weddings" and "Corporate events", when the caterer page renders, then both appear under the heading "Occasions".
2. Given a caterer saves with no occasion selected, when the save runs, then it is rejected with the message "Choose at least one occasion".
3. Given a caller submits an occasion value that is not on the fixed list, when the request is processed, then it is rejected with HTTP 400 and nothing is stored.

## L2-022: Enquiry form fields and validation
**Traces to:** L1-008

The enquiry form must capture the event date, guest count, event location, occasion and a message. All fields must be checked on the server, and also on the client for immediate feedback.

| Field | Rule |
| --- | --- |
| Event date | Required. Must be at least 2 days after today and no more than 24 months after today. |
| Guest count | Required. Whole number from 1 to 5,000. |
| Event location | Required. One service area from L2-010. Optional postal code, which is stored as the FSA only. |
| Occasion | Required. One value from the list in L2-021. |
| Message | Required. 20 to 2,000 characters, plain text. |

**Acceptance Criteria:**
1. Given a signed-in, verified customer fills in every field with valid values, when they submit, then the enquiry is created with status `Open`, the customer sees a confirmation that names the caterer, and the enquiry appears in both parties' inboxes.
2. Given today is 2026-10-10, when the customer enters an event date of 2026-10-11, then the error "Choose a date at least 2 days from today" appears and nothing is submitted.
3. Given today is 2026-10-10, when the customer enters an event date of 2028-10-11, then the error "Choose a date within the next 24 months" appears.
4. Given a guest count of 0, 5001, 12.5 or "fifty", when the customer submits, then the error "Enter a whole number of guests from 1 to 5,000" appears.
5. Given a message of 19 characters, when the customer submits, then the error "Tell the caterer a little more (at least 20 characters)" appears. Given a message of 2,001 characters, then the error "Keep your message under 2,000 characters" appears.
6. Given a direct API request that skips client checks and breaks any rule in the table, when the server processes it, then the response is HTTP 400 with an error for each failing field and nothing is created.
7. Given any validation error, when it is shown, then focus moves to the error summary and each error is linked to its field (L2-068).

## L2-023: Account and verified email required to enquire
**Traces to:** L1-008

Only a signed-in customer with a verified email address can send an enquiry. Customer registration asks for a display name (2–50 characters), an email address, a password (L2-076) and consent to the privacy notice (L2-070). Anything the visitor typed into the enquiry form before signing in must be kept.

**Acceptance Criteria:**
1. Given a visitor who is not signed in fills in the enquiry form and submits, when they are sent to sign in or register, then after they finish, the form is shown again with every value they entered.
2. Given a customer who has registered but not verified their email, when they submit an enquiry, then it is not sent and the message "Verify your email to send enquiries" appears with a "Resend verification email" control.
3. Given a customer verifies their email within 24 hours of saving an enquiry draft, when they return to the form, then the draft is still filled in.
4. Given a caterer account is signed in, when it opens another caterer's enquiry form, then the form is not shown and the message "Sign in with a customer account to send enquiries" appears.

---

## L2-024: Enquiry fit warnings
**Traces to:** L1-008

The form must warn the customer, without blocking them, when the enquiry falls outside what the caterer says they take on.

**Acceptance Criteria:**
1. Given a caterer whose guest range is 20–300, when the customer enters 500 guests, then the warning "This caterer usually serves 20–300 guests" appears next to the field.
2. Given a caterer who does not serve Oshawa, when the customer picks Oshawa as the location, then the warning "This caterer doesn't list Oshawa as an area they serve" appears.
3. Given a fit warning is showing, when the customer submits, then the enquiry is sent, and the caterer's view of it shows the same warning.

---

## L2-025: Enquiry abuse limits
**Traces to:** L1-008

The platform must limit how many enquiries one customer can send and block duplicates, to protect caterers from spam.

**Acceptance Criteria:**
1. Given a customer has sent 10 enquiries in the past 24 hours, when they submit an 11th, then it is rejected with HTTP 429 and the message "You've reached today's enquiry limit. Try again tomorrow."
2. Given a customer has an `Open` or `Replied` enquiry to caterer X for event date D, when they submit another enquiry to X for date D, then it is rejected with the message "You already have an open enquiry with this caterer for that date" and a link to the existing thread.
3. Given a customer account less than 1 hour old, when it submits enquiries, then at most 3 are accepted in that first hour.
4. Given the enquiry form is submitted, when the server receives it, then a bot-protection challenge token is required and checked (L2-082). A missing or invalid token is rejected with HTTP 400.

---

## L2-026: Responsive enquiry form
**Traces to:** L1-008

The enquiry form must suit each viewport class and use input types that bring up the right mobile keyboard.

**Acceptance Criteria:**
1. Given viewport XS or SM, when the enquiry form opens, then it fills the screen as a single column, and the submit button stays visible at the bottom of the screen.
2. Given viewport MD, LG or XL, when the enquiry form opens, then it appears in a dialog or side panel no wider than 640px, with the caterer's name and cover photo at the top.
3. Given a touch device, when the customer focuses the guest count field, then a numeric keypad appears (`inputmode="numeric"`). When they focus the event date field, then the device's native date picker appears.
4. Given the form is on screen at any viewport class, when the on-screen keyboard is open, then the field with focus is not hidden behind it.

---

## L2-027: New enquiry notification to caterer
**Traces to:** L1-009

When an enquiry is created, the platform must email the caterer at the address on their account. The email must not include the customer's email address or phone number.

**Acceptance Criteria:**
1. Given a customer sends an enquiry, when it is created, then the caterer is sent an email within 2 minutes (95th percentile).
2. Given the email is delivered, when it is opened, then it contains the customer's display name, event date, guest count, location area, occasion, the first 200 characters of the message, and a link to the thread.
3. Given the email is delivered, when its full contents are inspected, then the customer's email address and phone number do not appear anywhere, including headers. The `Reply-To` is a no-reply platform address.
4. Given the link in the email is opened by someone who is not signed in as that caterer, when the thread is requested, then they are asked to sign in, and the thread is shown only after signing in as that caterer.

---

## L2-028: Reply notification to customer
**Traces to:** L1-009

When a caterer replies in an enquiry thread, the platform must email the customer. Several replies within 10 minutes must be combined into one email.

**Acceptance Criteria:**
1. Given a caterer replies to an enquiry, when the reply is saved, then the customer is sent an email within 2 minutes (95th percentile), naming the caterer, showing the first 200 characters of the reply and linking to the thread.
2. Given a caterer sends 3 replies to the same thread within 10 minutes, when notifications are processed, then the customer gets 1 email that mentions 3 new messages.
3. Given a customer replies to a caterer, when the reply is saved, then the caterer gets an email under the same rules as criteria 1 and 2.
4. Given a caterer declines an enquiry (L2-033), when the decline is saved, then the customer is sent an email within 2 minutes saying the caterer can't take on the event, including any decline note.

---

## L2-029: In-app unread indicators
**Traces to:** L1-009

## L2-030: Email delivery reliability
**Traces to:** L1-009

Notification emails must be sent through a queue that persists, so a failed send does not lose the notification or fail the action that caused it. Sending domains must be authenticated.

**Acceptance Criteria:**
1. Given the email provider is unavailable, when a customer submits an enquiry, then the enquiry is still created and confirmed to the customer, and the notification is queued.
2. Given a queued notification fails to send, when retries run, then the platform retries with exponential backoff for up to 24 hours before marking it `Failed` and raising an operator alert.
3. Given a notification email bounces permanently, when the bounce is received, then the recipient's email is marked undeliverable, and the next time they sign in they are shown a banner asking them to update it.
4. Given the sending domain, when its DNS is inspected, then SPF, DKIM and DMARC (policy `quarantine` or stricter) records are present and outgoing mail passes all three.
5. Given any notification email, when it is inspected, then it is marked as transactional and contains no marketing content.

## L2-033: Enquiry status lifecycle
**Traces to:** L1-010

An enquiry must always have one of these statuses: `Open` (just sent, no reply from the caterer yet), `Replied` (the caterer has replied at least once), `Declined` (the caterer declined it) or `Closed` (either party closed it, or it was closed automatically). Only the transitions below are allowed.

| From | To | By |
| --- | --- | --- |
| Open | Replied | First caterer reply |
| Open | Declined | Caterer, with an optional note of up to 500 characters |
| Open, Replied | Closed | Customer or caterer |
| Open, Replied | Closed | System, 30 days after the event date |

**Acceptance Criteria:**
1. Given an `Open` enquiry, when the caterer sends their first reply, then the status becomes `Replied`.
2. Given an `Open` enquiry, when the caterer declines it with the note "Fully booked that weekend", then the status becomes `Declined` and the note appears in the thread.
3. Given a `Replied` enquiry, when the caterer tries to decline it, then the request is rejected with HTTP 409 and the status does not change.
4. Given an `Open` or `Replied` enquiry whose event date was 30 days ago, when the daily maintenance job runs, then the status becomes `Closed`.
5. Given a `Closed` or `Declined` enquiry, when anyone tries to change its status or add a message, then the request is rejected with HTTP 409.

**Acceptance Criteria:**

## L2-041: Photo upload checks and processing
**Traces to:** L1-012

Uploaded photos must be checked and processed on the server before anyone else can see them.

**Acceptance Criteria:**
1. Given a JPEG, PNG, WebP or HEIC file of up to 15 MB whose shorter side is at least 800 pixels, when the caterer uploads it, then it is accepted and a preview appears within 10 seconds.
2. Given a file over 15 MB, or one whose shorter side is under 800 pixels, when it is uploaded, then it is rejected with the message "Photos must be under 15 MB and at least 800 pixels on the shorter side".
3. Given a file whose extension says `.jpg` but whose content is not a supported image (checked by the file's content signature), when it is uploaded, then it is rejected and nothing is stored.
4. Given an accepted photo that contained EXIF GPS coordinates, when the processed versions are downloaded, then they contain no EXIF, XMP or IPTC metadata.
5. Given an accepted photo, when processing finishes, then the platform has re-encoded it to AVIF, WebP and JPEG at widths 400, 800, 1200 and 2000 pixels (never enlarging), and the original upload is not publicly reachable.
6. Given any uploaded file, when it is processed, then it is scanned for malware before any derived image is created. A file flagged as malicious is deleted and the event is logged.

## L2-076: Authentication
**Traces to:** L1-021

## L2-078: Session management
**Traces to:** L1-021

| Role | Idle timeout | Absolute timeout |
| --- | --- | --- |
| Customer, Caterer | 14 days | 30 days |
| Operator | 30 minutes | 12 hours |

**Acceptance Criteria:**

## L2-080: Input validation and output encoding

3. Given the 5xx error rate is above 2% for 5 minutes in a row, or the p95 listing latency is above 1 second for 10 minutes, when the condition is met, then an alert is sent to the on-call channel within 2 minutes.
4. Given any unhandled exception, when it happens, then it is recorded with a stack trace and correlation ID, and the user sees a generic error page that gives the correlation ID and no internal details.

## L2-090: Backup and recovery
**Traces to:** L1-023

Data must be backed up so that the platform can be restored with no more than 15 minutes of data lost (recovery point objective, RPO) and within 4 hours (recovery time objective, RTO).

**Acceptance Criteria:**
1. Given the production database, when its backup configuration is inspected, then point-in-time recovery is enabled with 35 days of retention, and the backups are encrypted and stored in a different Canadian region from the primary.
2. Given uploaded photos and certificate files, when storage is inspected, then versioning or replication to a second Canadian region is enabled.
3. Given a quarterly restore drill, when the database is restored into an isolated environment to a chosen point in time, then the restore finishes within 4 hours, the data matches that point to within 15 minutes, and the result is recorded.

## L2-091: Graceful degradation
**Traces to:** L1-023

If a dependency fails, the platform must keep its core functions working, with limited features where needed, rather than failing completely.

**Acceptance Criteria:**
1. Given the email provider is down, when customers send enquiries and caterers reply, then those actions succeed and notifications are queued (L2-030).
2. Given the image processing service is down, when a caterer uploads a photo, then the upload is accepted and marked "Processing", and it is published automatically once processing recovers.
3. Given the CDN is serving images but the application servers are overloaded, when visitors browse, then cached listing and caterer pages are still served (stale-while-revalidate up to 10 minutes).
4. Given the bot-protection provider cannot be reached, when a protected form is submitted, then the platform switches to stricter rate limits (half the normal thresholds) instead of blocking every submission, and raises an alert.

## L2-104: Launch list security
**Traces to:** L1-021

The launch list API is open to anyone, so it must resist abuse: guessing tokens, flooding inboxes, enumerating addresses and automated sign-ups.

**Acceptance Criteria:**
1. Given the backend's endpoint catalogue, when the launch list routes are listed, then the sign-up, confirm and removal routes declare `anonymous` as an explicit policy, and no route returns any list record, address or count to the public.
2. Given a confirmation or removal token, when it is created, then it has at least 256 bits from a cryptographically secure random source, only its SHA-256 hash is stored, and it is compared in constant time. A confirmation token is single-use and expires 48 hours after it is sent; a removal token lasts until its record is deleted.
3. Given the sign-up, confirm and removal requests, when they are sent without a valid CSRF token or from an origin not on the allow-list, then they are rejected with HTTP 403 (L2-081), except the RFC 8058 one-click `POST`, which is authorised by its removal token alone and can only delete.
4. Given a sign-up submitted without a valid bot-protection token, when the server receives it, then it is rejected with HTTP 400 and nothing is stored; and given the bot-protection provider cannot be reached, then the server applies half the rate limits in criterion 5 instead (L2-091). *(Needs a mock: how the challenge appears and fails on the launch page.)*
5. Given one IP address sends more than 10 sign-ups in an hour, or more than 30 confirm or removal requests in an hour, when the next one arrives, then it gets HTTP 429 with a `Retry-After` header.
6. Given a sign-up request body larger than 4 KB, when it is received, then it is rejected with HTTP 413.
7. Given a business name such as `<img src=x onerror=alert(1)>` or one containing line breaks, when it is submitted, then it is rejected or shown only as literal text, and no submitted value can add or change an email header (L2-080).
8. Given the launch site's responses, when their headers are inspected, then they meet L2-081, including a `Content-Security-Policy` with no `unsafe-inline` or `unsafe-eval` in `script-src`.
9. Given the API starts with a database and no Turnstile secret, when `BOT_CHALLENGE` is not explicitly `off`, then it refuses to start; and given an operator sets `BOT_CHALLENGE=off` because the Turnstile widget does not exist yet, when the API starts, then it reports that bot protection is off, accepts the local stand-in tokens the launch site issues when built without a site key, still rejects a sign-up without a token (criterion 4), and the delivery workflow warns on every run until `TURNSTILE_SITE_KEY` and `TURNSTILE_SECRET` are set.

Terms used in this section:

- **Directory:** the operator-curated records of places and events (A-9). Nothing in it is shown to visitors or customers in this release.
- **Place:** a storefront business (type Restaurant, Takeout, Grocery store or Bakery) or a Food truck. A place has the status `Listed`, `Draft` or `Closed`.
- **Storefront:** a place of any type other than Food truck. It has a street address and a map position.
- **Event:** a dated happening of type Festival, Market, Trade show, Food truck stop, Pop-up or Workshop. An event has the status `Draft`, `Scheduled` or `Cancelled`; a scheduled event whose last occurrence has ended shows as `Ended`.
- **Occurrence (stop):** one dated run of an event. A one-off event has one occurrence; a repeating event has one per repeat (L2-125). The mocks call a repeating event's occurrences "stops".
- **Vendor:** a directory place linked to an event.
- **Undo window:** the 10 seconds after a deletion during which it can be undone (L2-119, L2-129).
